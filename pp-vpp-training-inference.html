什么时候用 PP，
什么时候值得加 VPP？

PP 解决“模型如何跨设备放下和执行”；VPP 调整同一组设备上的层段与调度，让训练流水线有机会少等一会儿。选择取决于显存、可流水化工作量、网络与延迟目标。

PP：按层分区VPP：每卡多个虚拟段训练 / 推理分别判断

01 / SCENARIO FIRST

先用场景决定方向

训练：容量与大规模扩展

模型、梯度和优化器状态放不下，或 TP 跨节点通信过重：考虑 PP。已有 PP 且气泡明显、每段计算足够大：评估 VPP。

Prefill：长输入与吞吐

多请求或支持正确依赖的输入分块能形成流水线。长上下文场景可评估 PP + chunked prefill；是否降低 TTFT 要实测。

Decode：容量与并发

模型放不下时 PP 很有价值；高并发可填流水线。低并发、严格逐 token 延迟目标下，增加 PP / VPP 往往需要谨慎。

任务 / 约束PPVPP主要判断依据
全参数预训练；跨多节点；训练状态超容量优先考虑PP 气泡大时评估分层后的状态能放下；microbatch 足够；网络能承担边界通信。
训练 PP 已开启，m 与 p 接近先调平衡与 microbatch通常值得试验有可节省的气泡，同时 chunk 仍然有足够计算量。
小模型；单卡或单机 TP 已满足容量；少量 microbatch 微调收益可能有限通常低优先级流水线启动、通信与框架复杂度可能超过收益。
模型大到一个 TP / EP 组放不下的推理服务容量驱动不会额外缩小同卡总权重先让最大 stage 放下权重、KV 和 workspace，再优化吞吐。
长 prompt，支持 causal chunked prefill值得评估依赖推理引擎支持分块的层内 KV 依赖正确；计算与通信可重叠；TTFT / 吞吐联合测量。
高并发 decode；看重总 tokens/s可通过请求批次填充不能套用训练收益检查每个 stage 的队列、KV 容量及 p99 ITL。
单请求 / 低并发 decode；追求最低 ITL尽量小，但服从容量通常不宜优先下一个 token 必须等当前 token 完成，虚拟段增加串行传输边界。

p = 物理 PP stage 数；m = 每个数据并行副本每轮的 microbatch 数。以上是机制驱动的选型建议，最终以相同任务和 SLA 的测试结果为准。

02 / MODEL PLACEMENT

PP 与 VPP 到底切了什么？

PP（Pipeline Parallelism，流水线并行）按层切模型；VPP（Virtual Pipeline Parallelism，虚拟流水线并行）把每个物理 stage 再分成多个 model chunk。以 32 层、4 个物理 stage 为例。一个 stage 可以是一张 GPU，也可以是多张 GPU 组成的 TP / EP 组；图中的“GPU”先用单卡方便理解。

两种分配都让每卡持有 8 层。VPP2 把 8 层拆成两个 4 层 chunk，每卡总层数与总计算并没有再次减半。同一 GPU 上的 chunk 共享计算资源；调度把不同 microbatch 的前后向插入空闲机会。

在这个 round-robin 示例中，普通 PP 每个 microbatch 的前向有 3 次跨卡边界，VPP2 有 7 次。训练还要逆向发送激活梯度；这就是“更少气泡”和“更多通信”的交换。实际框架可支持其他 layer layout，边界数量与拓扑要按真实布局重新算。

GPipe / Fill–Drain所有 microbatch 前向完成后，执行所有反向。容易理解，形成前向和反向的流水波。保留很多未反传激活；每轮填充和排空。
非交错 1F1BWarmup 后，在本 stage 交替执行一个前向、一个反向；最后 cooldown。反向更早消费激活，通常比 GPipe 降低激活驻留。仍有流水线两端的气泡；不是同卡前后向同时执行。
VPP / Interleaved 1F1B每卡多个 chunk，交错不同 chunk 与 microbatch 的前后向。理想平衡情况下，缩短气泡对应的 chunk 时间。更多边界通信；更复杂的激活队列、梯度同步与参数布局。
全局 batch（普通 DP×TP×PP，无特殊复制）：B_global = DP × b_micro × m
普通 PP 理想训练时间：T ≈ (m + p − 1) × (t_F + t_B)
气泡相对有效计算的开销：O_bubble ≈ (p − 1) / m
气泡占总时间的比例：f_idle ≈ (p − 1) / (m + p − 1)
VPP 常用理想近似：O_bubble,VPP ≈ (p − 1) / (m × v)

例如 p=8、m=8 时，普通 PP 的理想空闲占比约 46.7%；m=64 时降到约 9.9%。v=2 的理想气泡缩减常用 1/v 估计，但并非每个实际 schedule 都严格达到：前后向耗时、group size、尾组、通信与非均匀层会改变结果。

什么情况适合训练 VPP？

已经需要 PP，普通 1F1B 的 GPU 空闲明显；允许足够的 microbatch；拆小后的 chunk 仍能高效运行；P2P 网络快且能重叠；训练框架支持该模型和布局。

什么情况应先优化别处？

m 很大、气泡已小；通信或 EP all-to-all 已是瓶颈；chunk 太小造成 kernel / 通信启动开销占主导；stage 不平衡严重；全局 batch 限制导致流水线无法填充。

这里讨论同步、每轮更新一次参数的训练 PP。异步流水线、weight stashing、Zero Bubble 及前后向重叠属于其他调度设计，不能直接套用本页公式。训练 m 在固定全局 batch 下增大时，b_micro 需相应减小，可能损害 GEMM 效率。

边界 tensor 字节：S = b × s × h × d
单次发送成本：τ = α + S / BW
训练边界消息总数：N_PP = 2m(p−1)，N_VPP = 2m(pv−1)

敏感性时间：T_proxy = T_schedule + ΔT

按 round-robin layer layout，每次边界同形状、同 dtype，前向与激活梯度大小相等；k 从布局计数。BW 使用十进制 GB/s，容量用二进制 MiB。通信代理项用最忙 rank 的总发送工作量，不模拟收发 rendezvous、链路竞争、TP / EP collective 和方向差异；并非精确 critical path。

调度中 F:B=1:2，均衡 stage、均衡 chunk，单个 chunk 时间按 1/v 分割；m 自动保持不小于 p 且为 p 的倍数，group size=p，以满足该源码版本的 VPP group 限制。无优化器 step、DP 同步、重计算或网络耗时。计算器允许改变通信 tensor 大小而保持计算时间不变，用于敏感性探索；实际 shape 改动应重新测量 compute time。

普通 PP / VPP 比较使用同一物理设备数、同一 m、同一 tensor shape 和总计算量。GPipe 与非交错 1F1B 在理想模型中气泡可能相近，但激活驻留方式不同。网页检查依赖和不重叠，仅证明教学模型一致。

05 / TWO DIFFERENT INFERENCE PHASES

推理中，Prefill 与 Decode 必须分开看

Prefill：有输入分块，才有流水机会

一次处理很多 prompt token。多请求批次可以像工件一样经过 stage。对单个 causal prompt，支持分块的引擎可以让早期 chunk 进入下游 stage，后续 chunk 在上游继续执行。

关键依赖：同一层的后续 chunk 必须能看到前缀 chunk 的 KV；KDA / 其他状态层还需传递正确的前缀状态。不能把每个 chunk 当成互相独立的完整 attention。

Stage 0: chunk 0 → chunk 1 → chunk 2
Stage 1: 等待 → chunk 0 → chunk 1 → chunk 2
Stage 2: 等待 → 等待 → chunk 0 → chunk 1 …

示意忽略通信。每层按 chunk 顺序维护 KV / 状态；跨层允许流水。

Decode：下一 token 不能提前执行

同一请求的 token t 经全部层得到 logits、采样出 token 后，才能执行 token t+1。把层分成更多虚拟段，无法解除这个依赖。

请求 A：token t → 所有 stage → 采样
→ token t+1 → 所有 stage → 采样

高并发：用 B、C、D 等请求 / 批次
占据 A 已经过的 stage

多个独立请求可以提升稳态吞吐，但要承受排队与调度开销。Decode 常受权重读带宽、KV 读写或小 batch 效率影响；过小 microbatch 可能放大这些问题。

仅前向、平衡 p 段、m 个独立工作项：T ≈ (m+p−1) × t_stage
单请求单 token：T_token ≈ Σ_j compute_j + Σ_boundary exposed_P2P + sampling / return
固定总层计算下，VPP 增加逻辑边界，不能把单 token 路径简单除以 v。
“Forward-only VPP 可执行”不等于“服务 decode 一定更快”。Megatron 源码有 forward_only 路径，此时全部工作项走 forward warmup；训练交错 1F1B 的反向填空机会已经不存在。推理要按实际引擎的请求调度、batch 组织与链路成本重新评估。

长上下文 PP：为什么 chunk 大小也很关键？

chunk 太大：工件少，难填满流水线，峰值 activation / workspace 可能大。chunk 太小：GEMM 规模缩小、消息数和 CPU 调度开销增加。随着 prefix 增长，同样 token 数的 chunk 运行时间也可能变化，导致 stage 等待传播。动态 chunking 可以尝试对齐工作项时间；是否有效要用目标模型和设备重新测量。

上述 chunked prefill 图为依赖示意；Megatron forward_only 机制见固定官方源码。PP 在层边界传输中间 hidden state / proxy tensor；它不等同于 CP 中跨卡合并同一层 attention 的部分输出和 LSE。

06 / CAPACITY BUDGET

PP 能分摊哪些内存，VPP 又改变哪些？

内存项增加物理 PP stage固定 p 增加 VPP chunk
GPU 权重每 stage 只持有分配的层；理想均衡约 1/p。同卡 chunk 权重求和；理想总量基本不变。
训练梯度 / 优化器 / master weights层归属随 PP 切分；DP sharding 再按配置处理。总层归属未减少；可能改变 bucket、同步与 padding。
训练激活由层数、未完成 backward 数、调度和 checkpointing 共同决定。chunk 小，但驻留队列改变；不能普遍承诺降到 1/v。
推理 KV / recurrent state一般由本 stage 的 attention / 状态层持有；TP / CP 布局另算。层总数不变；请求 / microbatch 驻留数可能变化。
通信 buffer / workspace / graph pool增加 buffer、异步工作和 stage 端点管理成本。更多 chunk / 消息队列 / graph，可能增加峰值。
CPU RAM / 加载峰值取决于实际 rank 是否只读取自己 shard、共享 mmap 或全模型 staging。不会自动按 v 降低；若每 rank 全量读取 checkpoint，CPU 峰值仍大。
GPU_j = Σ_(本 rank 持有的层) [权重 + 梯度 + 优化器状态 + KV / 状态]
+ peak_activation_j + workspace_j + comm_buffers_j + graphs_j + reserve_j
节点 CPU RAM = Σ_(本节点 rank 的独占加载 / offload / pinned buffers)
+ 共享页实际占用 + OS / 服务预留
可运行条件：每一张卡 / 每一个节点的峰值都小于各自可用容量。

一个可复算的训练容量示例

仅作为示例：70B 参数、BF16 参数 2 B、FP32 梯度 4 B、FP32 master 4 B、Adam m/v 共 8 B，总持久训练状态为 18 B/参数。若无 TP、无 DP sharding、均匀 PP4，每卡基础状态 ≈ 70×10⁹×18/4/2³⁰ = 293.37 GiB，尚未计激活与临时空间。VPP2 仍约 293.37 GiB；PP8 的均匀基础值约 146.68 GiB。

这不是所有训练配方的固定字节数：梯度 dtype、优化器、master weights、FP8 元数据、ZeRO / FSDP 都会改变状态量。LoRA 的可训练状态小很多，但基座权重与激活仍需预算。

不要用总权重 / 总 GPU 数作为最终容量判断。Embedding、LM head、不同层类型、shared expert 和复制张量会让 stage 不均匀；应计算最大 stage / rank。优先按实际计算时间与内存双重平衡，而不是只按层数平均。

同样的规则也适用于推理权重

教学示例：400B 参数、BF16 权重 2 B，均匀 PP4、无其他 sharding，则每 stage 基础权重约 400×10⁹×2/4/2³⁰ = 186.26 GiB。固定这 4 个物理 stage 增加 VPP2，每 stage 的两个 chunk 加起来仍约 186.26 GiB，KV / 状态、workspace 与复制张量需另算。

这里使用理想均匀的虚构模型来复算容量；不是具体机器环境或线上模型报告。

07 / PARALLELISM COMPOSITION

通常是 PP 配合其他并行

策略与 PP 的关系选型重点
TP / Tensor Parallel一个 stage 内拆矩阵；PP 跨 stage 拆层。常见做法是 TP 放快速互联域，PP 跨域；但现代跨节点 fabric 可能足以支撑大 TP，应比较通信与延迟。
DP / Data Parallel复制整个 PP×TP 流水线处理不同数据。固定全局 batch 时增大 DP 会减少每流水线 m，气泡可能更大；推理副本增加需额外复制模型。
EP / Expert Parallel在各 PP stage 的 MoE 层分配专家。检查 EP 是否是 DP / TP rank 的重新分组；不能默认将 EP 再乘一次算 GPU 数。EP all-to-all 与 PP P2P 可能争用网络。
CP / Context Parallel切同一层的序列 / KV 工作；PP 切不同层。长上下文容量与算力的另一条路线；并非所有推理框架和模型支持 PP+CP 的组合。
ZeRO / FSDP / Activation Checkpointing进一步降低状态或激活内存。新 all-gather / 重计算会改变 stage 时间与 VPP 的最佳 chunk 粒度；需重测。
普通三维训练并行示例：GPU 数 = DP × TP × PP
例：DP4 × TP8 × PP4 = 128 GPUs
VPP2：仍然 128 GPUs，每物理 stage 有 2 个 model chunk。
EP / CP / AttentionDP 是否额外占设备，需读取真实 process-group 布局。

如果 stage 本身是 TP8，跨 stage 传的是各 rank 对应的 hidden tensor 或 shard，具体随 SP / TP 布局变化；本页计算器的 S 是“一条 P2P 消息”的假设大小，不是整个 stage 组的聚合流量。

08 / PRACTICAL WORKFLOW

实际部署：先满足容量，再比较收益

确定目标与负载

训练：固定模型、token/global batch 和收敛配方，优化 step time / MFU。Prefill：固定输入长度分布，比较 TTFT 和吞吐。Decode：固定并发、上下文与输出长度，比较 ITL、p99 和 tokens/s。

计算每 rank 与每节点峰值

先选能容纳全部状态的最小合理 PP；把 endpoint、专家复制、非均匀层、KV 和加载峰值计入。VPP 作为调度优化，不能补救基础权重超容量。

建立普通 PP 基线

训练用非交错 1F1B；调平 stage、m 与 microbatch size。推理调 chunk size、batch depth 和并发。记录每 stage 计算、等待、P2P 时长、峰值显存与网络利用率。

只在存在可节省气泡时试 VPP

从 v=2 比较，再尝试更细粒度；保持模型、GPU、全局 batch 与 dtype 相同。若通信等待、chunk 启动开销或显存增加抵消气泡收益，回到普通 PP 或重新切层。

验证最终目标，而不是只看时间线漂亮

训练验证 loss / 梯度与保存恢复；推理验证 logits / 输出和 KV / 状态正确性。记录稳定重复测量和 p95 / p99；TTFT、ITL 与吞吐可能朝不同方向变化。

核对框架配置，避免同名术语误用

推理引擎的 PP stage 数、microbatch size 和异步 batch depth 是不同配置。batch depth 描述流水线中可驻留的批次，不等于每 stage 的 VPP model chunk 数。CP 的 interleave 也可能指序列分片，不能据此判断支持 VPP。

开启训练 VPP 应确认模型以多个 chunk 构建，并选择支持该布局的交错调度；推理还需确认请求、KV / recurrent state、采样回传和 CUDA Graph 的兼容性。只有某个 PP 参数存在，不足以证明该版本支持 VPP。

09 / CHECK YOUR UNDERSTANDING

六个容易混淆的问题

PP 能让一个样本的不同层同时执行吗？

同一个 microbatch 的普通前向层之间有依赖，必须先有上层输出。PP 并行来自不同 microbatch、请求或有序 prompt chunk 占据不同 stage；不是让依赖层凭空同时计算。

VPP2 是否等于 PP 数乘以 2，显存再除以 2？

逻辑层段更多，但物理设备没有增加。每卡多个 chunk 的权重必须相加，计算资源也共享。VPP 主要改变调度和通信，基础模型状态并没有按 v 再分摊一次。

训练 microbatch 越多越好吗？

多工件可以减少相对气泡，但固定全局 batch 下 microbatch size 会变小，可能降低算子效率；动态变更全局 batch 还会影响优化配方。要联合检查 step time、显存与收敛。

VPP 总能减少 activation memory 吗？

不能。虽然 chunk 较小，但未完成 backward 的 chunk 数与 warmup 队列会变。重计算、异步通信 buffer、梯度桶和图池共同决定峰值，应实测各 rank。

Chunked prefill / 多 stream / continuous batching 就是 VPP 吗？

不是。Chunked prefill 切输入工作量，多 stream 处理执行重叠，continuous batching 管理请求批次；VPP 是把每个物理 stage 的模型层切成多个虚拟段并调度它们。它们可以配合，但概念不同。

什么时候 PP 会降低低并发推理延迟？

是否降低取决于基线。若替代跨慢链路的大 TP、CPU offload 或超容量方案，PP 可能改善延迟；若基线已是单互联域高效执行，PP 的额外边界与填充通常需要付出代价。长 prompt 分块还可能形成层间流水，需用相同 prompt 对比 TTFT。
