01 / 最重要的结论

可以运行 V4.1-Flash 离线推理；当前不能直接启动完整 PD 在线服务

当前已提供模型运行与推理引擎

优化算子、EP/EPLB、Attention DP/CP、调度、采样、DSpark、结构化输出，以及离线生成、benchmark、评测示例。

发布范围外完整在线服务层

外部 KV cache 系统、VE/P/D 分离服务编排与路由、P/D 数据并行副本间负载均衡，没有以可直接部署的完整服务公开。

适用范围明确一个模型家族，两类硬件

官方支持 DeepSeek-V4.1-Flash；硬件是 NVIDIA SM100 和 Huawei Ascend 950。H20、MI355X 与任意 HF 模型不在当前支持清单。

不要把三个“有”误读为“能直接上线”：有 EngineType.PROMPT/COMPLETION，有生产 E/P/D 架构说明，有分别测 Prefill/Decode 的脚本；但这三者没有构成已交付的前端 API + KV 传输 + 路由 + 故障处理服务。

README 的定位是“来自 DeepSeek 大规模生产服务的高性能推理框架”，但开源范围明确为 offline inference。仓库创建于 2026-10-16，本页锁定的提交时间为 2026-10-20；没有把仓库内部 0.1.0 当作已发布且完整认证的发行版。

直接证据：README 的功能/硬件/不含组件列表；PD 与 KV 钩子的实际实现。

    一次离线请求的实际路径

    PYTHON INTERFACE

    接口与使用：从 LLM.generate 到引擎步进

    最直接的调用入口是 deepinfer.entrypoints.llm.LLM。公开仓库提供离线批量生成接口和底层引擎；这里没有可直接套用的 deepinfer serve、OpenAI HTTP server 或 /v1/chat/completions 入口。源码来自 vLLM 并不代表接口与最新 vLLM 兼容。

    正确导入方式
    from deepinfer.entrypoints.llm import LLM
from deepinfer.engine.arg_utils import EngineArgs
from deepinfer.engine.llm_engine import LLMEngine
from deepinfer.sampling_params import SamplingParams

    本快照的顶层 deepinfer/__init__.py 没有导出 LLM 或 SamplingParams；不要照搬 from vllm import LLM, SamplingParams 的导入形态。

    入口职责与真实行为调用时注意
    EngineArgs(model, ...)模型、DP/CP/EP、内存、调度配置的 dataclass。没有通用的 tensor_parallel_size 参数；本实现以 Attention DP/CP 和 MoE EP 为核心。
    LLM(model, ..., **kwargs)构造 EngineArgs，建立 LLMEngine，自动设 offline_inference=True。完整分布式启动建议复用官方 examples/_launch.py 和 _config.py。
    LLM.generate(...)把批量请求入队，反复 step，最终按输入顺序返回。decode_sequence=True（构造默认值）返回字符串列表；False 返回每个请求的逐 token 输出列表。
    SamplingParams(...)温度、top-p/top-k、最大 token、结构化输出、序列随机种子。默认 max_tokens=16；logprobs 是被忽略的兼容参数。读取 token_logprobs / top_logprobs 字段。
    LLMEngine.from_engine_args(args)低层构造，适合引擎扩展。只是构造接口，不会自动补齐集群 launcher、路由和 PD 传输。
    add_request(...)创建 Sequence 并入队；输入为 token IDs。需要 user_id、唯一 request_id 和一维 np.int32 数组；字符串须先 tokenize。
    step() / flush_inflight_reqs()驱动一轮调度和模型执行 / 排空异步在途输出。原始返回是 np.ndarray[np.uint64] 指针数组；通过 RequestOutput.clone(ptr) 保留输出。
    abort_request(id) / close()取消请求，或关闭 worker 与多模态/语法处理资源。外层用 try/finally: llm.close()；一次完整运行结束主动释放。

    源码：LLM · EngineArgs · SamplingParams · 引擎构造与入队

    关键参数：控制“模型一次能处理多少”与“怎么分到多卡”

    参数含义该快照默认值
    data_parallel_sizeAttention 数据并行引擎数；须结合 launcher、CP 与 EP 配置。0，实际示例显式传入
    context_parallel_size同一引擎内的上下文并行规模。1
    expert_parallel_sizeMoE 专家分布的通信组规模；可跨 Attention DP/CP。1
    max_num_batched_tokens调度 token 预算；prefill chunk 的大小会影响吞吐、显存及延迟。None，由配置后续推导
    max_num_seqs可并行处理的序列上限。256
    max_model_len允许的模型上下文长度；须能落入实际 KV 容量。None，由模型配置推导
    gpu_memory_utilization引擎预算的显存使用比例；过高可能导致图捕获或运行时 OOM。0.90
    engine_typeNORMAL / PROMPT / COMPLETION。NORMAL；枚举不等于已具备完整 PD 服务
    chunked_prefill把长 prompt 拆成多个调度块。EngineArgs 为 False，官方 create_llm 设为 True

    先使用已存在的启动器，再修改业务输入

    以下代码基于官方 examples 的配置与进程启动方式改写。它是单节点 8 卡、EP8 / DP8 / CP1 的模板：每个 Attention DP rank 执行一份输入，MoE 的 EP 跨 rank 组协作。这不是 8 份相互独立的完整模型。显存与互联仍须满足目标模型要求；代码未在 GPU 上运行验证。

    最小业务示例 · examples/my_client.py
    # 保存到 DeepInfer 仓库的 examples/my_client.py
# 复用官方启动器：单节点 8 卡、EP8 / DP8 / CP1。
# 需要先完成官方构建、模型下载和显存容量确认。
import os
from _config import DEFAULT_MODEL_NAME, create_llm, setup_common_env
from _launch import launch_dp


def main(dp_size: int, dp_rank: int) -> None:
    # 在导入 deepinfer / 初始化设备前设置环境。
    os.environ["DEEPINFER_USE_NEXTN_DECODE"] = "0"
    os.environ["DEEPINFER_ENABLE_MTP_VARLEN"] = "0"
    setup_common_env(
        model_name=DEFAULT_MODEL_NAME,
        sampler_force_topk=4096,
        set_override_experts=True,
        enable_eplb=True,
    )
    llm = create_llm(
        DEFAULT_MODEL_NAME, dp_rank,
        ep_size=8, cp_size=1,
        data_parallel_size=dp_size,
        max_num_batched_tokens=32768,
        max_model_len=32768,
        max_num_seqs=4,
        gpu_memory_utilization=0.85,
        decode_sequence=False,
    )
    from deepinfer.sampling_params import SamplingParams
    try:
        # 原始补全文本；对话模板需调用方按模型要求准备。
        results = llm.generate(
            prompts=["问题：中国的首都是哪里？\n答案："],
            sampling_params=SamplingParams(
                temperature=0, max_tokens=128, seq_seed=42
            ),
            use_tqdm=False,
        )
        for tokens in results:
            text = llm.get_tokenizer().decode(
                [t.token_id for t in tokens], skip_special_tokens=True
            )
            print(f"rank={dp_rank}: {text}")
    finally:
        llm.close()


if __name__ == "__main__":
    launch_dp(main, dp_size=8)

    依据：create_llm 与初始化顺序 · 进程启动器 · 官方完整 offline 示例

    generate 的真实签名与返回值
    LLM.generate(
    self,
    prompts: str | list[str] | None = None,
    sampling_params: SamplingParams | list[SamplingParams] | None = None,
    prompt_token_ids: list[list[int]] | list[np.ndarray[np.int32]] | None = None,
    use_tqdm: bool = True,
    multi_modal_data: dict | list[dict] | None = None,
) -> list[list[RequestOutput] | str]

    prompts 与 prompt_token_ids 至少提供一个；两者同时提供时批大小必须一致。对多条请求建议显式传入同长度的多模态列表。默认输出不是 vLLM 风格的 result.outputs[0].text；应根据 decode_sequence 选择直接读字符串，或拼接 token_id 后解码。

    RequestOutput 常用字段：request_id、token_id、finished、finish_reason、token_logprobs、prompt_len、draft_tok、accept_tok。投机解码可能一次 step 输出多个 token，不能把 step 数等同于生成 token 数。

    generate 签名 · RequestOutput 字段

    进阶：手动 add_request / step，为什么必须 clone？

    引擎底层通过输出池管理内存，下一次 step 会回收上一轮原始输出。官方 LLM 包装器使用 RequestOutput.clone(raw_output)。如果做流式封装，应及时复制或消费字段，并在队列空后处理异步在途结果。

    # 这段在已初始化好的 llm 所在 rank 内使用；不是独立启动器。
import numpy as np
from deepinfer._C.engine import RequestOutput
from deepinfer.sampling_params import SamplingParams

engine = llm.llm_engine
seq = engine.add_request(
    user_id="demo",
    request_id="req-1",
    sampling_params=SamplingParams(temperature=0, max_tokens=128),
    prompt_token_ids=np.asarray(
        engine.tokenizer.encode("问题：一年有几个月？\n答案："),
        dtype=np.int32,
    ),
    multi_modal_data={"image_bytes": [], "image_sizes": []},
)
if seq is None:
    raise ValueError("请求未入队，请检查 token 范围")

kept_outputs = []
while True:
    unfinished = engine.has_unfinished_requests()
    raw = engine.step() if unfinished else engine.flush_inflight_reqs()
    # raw 是 uint64 指针数组，必须在下一步复用池内存之前 clone。
    kept_outputs.extend(RequestOutput.clone(ptr) for ptr in raw)
    if not unfinished:
        break

text = engine.tokenizer.decode(
    [o.token_id for o in kept_outputs if o.request_id == "req-1"],
    skip_special_tokens=True,
)
print(text)

    取消时调用 engine.abort_request("req-1")，返回 (被取消序列数, 这些序列的 token 数之和)。应用层仍需实现 HTTP 请求断开、超时、背压、错误到响应的转换。

    官方 clone + drain 循环 · step 返回内存生命周期 · abort_request

    图片输入与 VE：在同一个引擎内完成编码

    VE 是 Vision Encoder（视觉编码器）。当前样例把原始图片字节与宽高传给引擎，CPU 预处理在 worker 中异步执行，GPU 上执行 pad → ViT → downsample → aligner，再把 image embeddings 写入 LLM 输入。这个 inline 路径已存在；独立 VE 服务的网络编排不在公开发行范围。

    import io
from pathlib import Path
from PIL import Image
from deepinfer.sampling_params import SamplingParams

binary = Path("examples/images/carrots.jpeg").read_bytes()
with Image.open(io.BytesIO(binary)) as image:
    width, height = image.size
processor = llm.llm_engine.multi_modal_processor
image_token = llm.get_tokenizer().convert_ids_to_tokens(
    processor.mm_config.image_token_id
)
results = llm.generate(
    prompts=[f"{image_token}\nQuestion: What is shown?\nAnswer:"],
    multi_modal_data=[{
        "image_bytes": [binary],
        "image_sizes": [(width, height)],
    }],
    sampling_params=SamplingParams(temperature=0, max_tokens=128),
    use_tqdm=False,
)

    图片 token 必须与图片列表顺序对应，采用当前模型 processor 的 token；这不是任意 VLM 的通用图片 API。

    其他模型能用吗？先看 Registry，再看 checkpoint 合同

    模型 / 输入当前公开快照结论判断依据
    DeepSeek-V4.1-Flash官方支持，默认 checkpoint 为 DeepSeek-V4.1-Flash-1017README、离线示例、唯一模型 Registry 项。
    V4.1 同架构的本地 checkpoint有条件：同架构不等于任意权重格式可用必须通过模型类型、量化配置、tensor shape 与权重完整性校验。
    DeepSeek-V3 / R1 / V3.2 等其他架构当前未注册，不可仅更换 model_name其架构字符串与配置不满足当前 loader；“DeepSeek”品牌相同不保证兼容。
    Qwen / Llama / 其他 Dense 或 MoE当前没有开箱支持没有对应 model class、config/weights adapter 和内核路径适配。
    任意 Hugging Face 模型 ID下载能力 ≠ 推理兼容性snapshot_download 只解决文件获取，之后仍会校验 architecture。

    具体限制：architectures 仅接受 ["DeepseekV41ForCausalLM"]；model_type 必须是 deepseek_v41。当前 loader 还校验 quant_method=fp8、expert_dtype=fp4、activation_scheme=dynamic、weight_block_size=[32,32]、scale_fmt=ue8m0。你此前使用的 FP8 A8W8 + K128 blockscale 合同不能直接替代这里的 checkpoint 合同。

    移植新模型至少涉及：模型类与 Registry → HF config/权重转换 → Attention/KV/state 布局 → 并行与通信 → 量化 kernel → tokenizer / 多模态处理 → 正确性与性能回归。仅修改 Registry 名称会把错误延后到权重加载或算子执行。

    唯一注册架构 · HF 类型与量化硬校验 · 不支持架构的报错

    设备当前快照如何判断
    B200 / SM100属于官方列出的 NVIDIA 架构仍需满足显存、驱动、CUDA 以及卡间互联要求；不能只看 GPU 名称。

    MI355X / gfx950未提供 ROCm 后端不能沿用此前 AITER/ROCm 环境直接启动。
    Huawei Ascend 950官方支持使用 CANN 9.2 与 Ascend 专用依赖。
    需要多少张卡？ 官方离线命令默认 EP8；NVIDIA 回归测试实际用 4 卡 / EP4 / CP2 / DP2。Ascend 回归用 2 节点 × 8 卡 / EP16 / CP8 / DP2。这是源码已有的测试配置，不是所有显存型号、上下文长度的最小卡数保证。生产文档中的“64P + 64D 最小高效部署单元”讨论的是生产效率。

    05 · 两节点启动：这是一个分布式离线作业

    下面是每节点 8 张 SM100 的 启动结构模板：总计 EP16、CP1、DP16。两节点均需相同源码、依赖、模型目录，以及受支持的 scale-up 互联；它不承诺普通以太网跨机可达到论文性能。需在两台节点各执行一次 Python 命令，不能把节点 0 理解为 Prefill、节点 1 理解为 Decode。

    # 两节点共同环境（各执行一次）；先替换地址与模型路径
export DEEPINFER_ACCELERATOR=nvidia
export DEEPINFER_HF_MODEL_DIR=/data/models/DeepSeek-V4.1-Flash-1017
export WORLD_SIZE=2
export MASTER_ADDR=192.0.2.10  # 示例地址：替换为节点 0 的可达地址
export MASTER_PORT=29500
export CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
export DEVICE_OFFSET=0
    # 仅在节点 0 执行
RANK=0 python examples/offline_inference.py --ep 16 --cp 1
    # 仅在节点 1 执行；与节点 0 的作业配合启动
RANK=1 python examples/offline_inference.py --ep 16 --cp 1
    • WORLD_SIZE=2 在这些示例里是 2 个节点；不是常见 torchrun 语义下的 16 个进程。
    • 内部 launch_dp() 会 spawn 本节点负责的 DP 进程，别再嵌套 torchrun --nproc_per_node=8。
    • 实际 TCP rendezvous 使用 MASTER_PORT − 50 + engine_group_rank；还要满足通信后端的网络与共享内存要求。两节点使用相同端口设置，并为并发作业分配不同端口。
    • CP 分组应能落在节点本地设备上；示例 launcher 还要求 DP % 节点数 == 0。

# Encoder：仅加载视觉编码侧权重，默认单设备扫图片 batch
bash examples/sweep/run_sweep.sh encoder ve-800
    指标 / 输出应该怎样理解
    avg_SPS稳态 steps/s，独立于你最后按何种接受率换算 token 吞吐。
    Decode tokens/s/GPU固定长度 benchmark 按满接受计算：SPS × batch × (1+nextn) / CP。不是直接测得的在线有效 token 吞吐。
    Pareto 图接受率绘图采用 τ=1+nextn×a，每用户速度 SPS×τ。传入 0.75 是假设，不会改变真实模型接受率。

    07 · 出问题时按这一顺序定位

    现象优先检查
    编译失败 / 找不到 CUDAGCC、Python、Toolkit 与 Torch cu132 是否匹配；虚拟环境是否激活；CXX11 ABI；是否保留子模块固定版本。
    加载 checkpoint 失败是否为完整 V4.1-Flash-1017 HF 目录；config.json 的 architecture、model_type、量化合同；权重分片是否齐全。
    多机启动一直等待两边是否都启动；节点 RANK 是否唯一；WORLD_SIZE 是否误填成 GPU 数；MASTER_ADDR、实际端口、通信拓扑。
    OOM显存容量与模型分片是否匹配；上下文、batch、CP、冗余专家、graph capture 占用。不要用“4 卡测试过”替代显存估算。
    吞吐曲线异常PROFILE 是否关闭；tag 是否混入不同模型/EP/CP/nextn；非缓存输入是否足够；是满接受估算还是实际有效 token。
    PREFILL / DECODE DISAGGREGATION

    能不能直接拉起 PD 分离的 DeepSeek？

    可以以它为基础开发；当前公开版不能靠两条现成命令启动完整 PD 服务。DeepSeek 的生产系统使用 E/P/D 分离，但本次仓库交付的是离线推理与核心引擎。README 明确将 KV 系统、阶段分离和 P/D 副本间负载均衡列为尚未包含的组件。

    先分清三个层级：① 算子能算 P 和 D → ② 引擎可分成 PROMPT / COMPLETION 两种角色 → ③ 请求路由、KV 传输、D 侧接力与容错组成线上服务。公开版已经深入到②；③仍需要你接齐。查看 README 原文 ↗
    能力当前公开版本意味着什么
    DeepSeek-V4.1-Flash 离线生成有用官方 checkpoint、支持硬件和 examples 先跑通。
    P / D 各阶段性能扫描有同一引擎运行 P 再运行 D，提取阶段指标；不是两池请求接力。
    独立 P / D 引擎模式有基础EngineType.PROMPT / COMPLETION 控制调度；还有 PD 扩展钩子。
    KV GPU 布局、状态切片与回填有原语已有 block cache / state cache、SWA 环形布局变换；不等于跨机 KV 服务。
    可部署的线上 PD / EPD 服务未完整提供需实现跨池路由、KV 传输、接力、背压和失败清理。
    DeepSeek-V3 / R1、Qwen、Llama未列为支持不能只替换 --model_name；模型注册表与 HF loader 均限定 V4.1。

    一次真正的 PD 请求，走哪条路？

    源码里哪些接口是“接线口”？

    # deepinfer/engine/llm_engine.py：这些方法的基础实现仅含说明文字
# 不是可直接调用的联网/传输实现，需在集成层实现。
def init_pd_split(self):
    "初始化 PD 分离需要的数据结构"

def send_processed_prompts(self):
    "把已处理完的 prompt 发送给 completion engine"

def do_save_kvcache(self, scheduled, finished):
    "保存 kvcache"

    看钩子的实际源码 ↗；看 P / D 调度分支 ↗。设置角色只改变“这个引擎计算哪一步”，不会自动建立网络服务、传 KV 或选择 D 节点。

    KV 不能只理解成一个要 memcpy 的张量

    术语 / 状态直观理解PD 集成时要处理
    Block KV分块保存的历史注意力状态，包含主 KV 和 indexer K 等。P、D 的 block id 不必相同；要分配接收空间并建立新 block table。
    SWA / state cache滑动窗口注意力的“最近一段记忆”，以及压缩过程状态。环形缓冲区、当前位置和状态槽位必须对应，不能只转 token ids。
    YOCO / bounded replay复用层间 KV，并在消费者层只重算有限后缀来恢复 SWA。这属于模型内部机制，不是把线上 P/D 服务自动拆开；恢复长度要覆盖窗口与回退余量。
    To store / To CE存储复用需要的状态与“继续 decode”需要的状态不同。TO_CE=True 包含完整 state；落盘只保留 stored region。落盘 128 对齐不等于 P→D 传输强制 128 对齐。
    Cache load / offload把状态回填到设备，或保存到主机/存储。已有局部回填与切片函数；跨机寻址、传输、完成事件、重试和释放仍需实现。

    关键接口：select_state_slice_to_store(..., TO_CE=True) / load_state_from_store_to_prefill_cache(...) ↗。生产 Q&A 还特别说明：decode 不做容量驱动的 KV offload，但会把新生成 KV 写入存储以便后续复用；二者不要混为一谈。

    如果必须用 DeepInfer 做线上 PD，按这四步落地

    1. 建立同池正确性基线。先跑官方 checkpoint 的 offline inference、数值验证和 benchmark，记录 token 输出、阶段耗时与资源占用；接入请求时间戳后再按明确口径测 TTFT。
    2. 补一条固定 P→D 通道。实现独立 PROMPT / COMPLETION 引擎集成，D 先预留 KV 与 state 槽位；P 计算完成后传完整数据与位置元信息，D 确认传输完成后再调度。
    3. 补服务生命周期。入口编码/解码、路由、请求 ID、流式返回、取消、超时、背压、资源释放与失败重试都要串起来；复制两份模型启动进程并不完成这一步。
    4. 再做存储与弹性。增加 prefix hit、KV 持久化、P/D 负载均衡、扩缩容。覆盖 128 边界、长上下文、MTP 回退、连接断开和 D 侧空间不足等验证。
    规模建议 ≠ 最低启动门槛。官方生产 Q&A 推荐 P 用 EP/DP 2–8、D 用 Wide-EP/DP 64–128，并给出 64P+64D 的“高效部署单元”建议；不能把它解读为代码至少需要 128 卡。官方性能图使用 P=4 SM100、D=64 SM100，各自位于同一 scale-up domain。部署 Q&A ↗

    其他模型怎么选？

    V4.1 同架构的检查点也需要通过当前 loader 的结构、量化和形状校验；V3、R1、Qwen、Llama 等则需要模型移植。若目标是尽快上线这些模型的 PD 服务，应优先考察已公开交付该模型部署闭环的 SGLang、vLLM 或 TensorRT-LLM，并核对具体版本、GPU、量化与 KV connector 支持范围。本页不把它们的命令冒充成 DeepInfer 命令。

    07 / 并行参数：不能套用其他框架的 rank 语义

    DP、CP、EP 是不同分工，节点数也不等于 rank 总数

    名称在这份仓库中的含义容易误读的点
    Attention DP不同请求/批次的 attention 工作分配与 MoE 专家切分共同组织；不是把完整模型简单复制到每卡。
    Balanced CP上下文相关工作在 CP 组内协作；示例支持 --cpREADME 列出 CP 能力；Q&A 生产配方“目前不使用 CP”是部署选择，两者不矛盾。
    MoE EP把专家分到不同设备，DeepEP 处理 token 通信实际跨卡依赖网络与拓扑，不是 GPU 数够就自动得到高效 Wide-EP。
    EPLB通过冗余专家和统计重新平衡专家负载公开的 EPLB 不等于公开了所有 P/D 实例之间的请求负载均衡。
    WORLD_SIZE / RANK（examples）launcher 用节点总数 / 节点编号分配本机 DP 进程不是直接照搬 torchrun 的“总进程数 / 全局进程rank”语义。
    DEVICE_OFFSET示例启动器选择本机连续设备区间的起点代码会重写可见设备变量；任意不连续掩码并不保证按你想象的卡号运行。
    生产 Q&A 提到 Prefill 采用 EP2–8，Decode 推荐 EP64–128；并称高效生产单元常见 64P + 64D GPU。这是其生产设计建议，不是“离线最少需要128卡”，也不是本仓库一条命令启动128卡PD的承诺。

    离线脚本的并行形状计算器

    下面只检查 offline_inference.py / _launch.py 的关键整数关系。它不估算权重显存，不检查所有模型或通信约束。

    DP 进程总数8
    逻辑设备规模 DP × CP8
    本机 DP 进程数8

    已核对关系：DP×CP % EP == 0，launcher 要求 DP % 节点数 == 0。页面按 DEVICE_OFFSET=0、各节点相同的物理设备数模拟官方取模选卡规则，提示越界/重叠；容器设备编号或偏移变化时仍需实查。不会宣称通过这些检查就一定能加载模型。

    08 / 不要把离线分阶段计时当成在线 PD 性能

    benchmark.py 分别测 P 和 D，仍然不等于部署了两个服务池

    官方示例在同一运行中构造请求、预热、推进 prefill 和 decode；decode 复用先前生成的共享 prefix KV。P 和 D 的 batch 参数可分别设置，这里的“decoupled”是工作负载与计时组织，并不是跨服务 KV 传输完成。

    指标 / 开关源码口径应该怎样使用
    Prefill throughput非缓存输入工作量，预热后取稳态间隔，按设备数量归一化与 context_length、non_cached_tokens、batch 和 CP 配置一起记录。
    Decode avg_SPS稳定窗口中的引擎步数/秒一步可能产生多个 token；不是每用户 token/s 的直接同义词。
    Decode tokens/s/GPUavg_SPS × decode_num_requests × (1+nextn) / cp，按满接受率计数并非真实草稿接受后的实际有效输出吞吐。应记录 nextn、真实接受率和线上调度开销。
    Decode Pareto 的 accept_rate画图脚本可按给定接受率缩放曲线0.75 等传入值是绘图假设，不是该次运行自动测出的接受率。
    PROFILE=1独立 profiler 窗口；示例文档说明采样会扰动 step 延迟trace用于看算子组成，不用trace中的慢step倒推稳态SPS。
    README性能图Prefill 4 SM100 GPU、Decode 64 GPU，均在一个scale-up domain内不能把图直接外推到单张B200、H20、MI355X或任意普通跨机网络。

    常见功能开关怎么理解

    功能明确设置说明
    DSpark / confidence-scheduled verificationDEEPINFER_ENABLE_MTP_VARLEN=1草稿 token 与按置信度安排验证；不能把draft token全算作已接受输出。
    最大草稿长度DEEPINFER_USE_NEXTN_DECODE，默认5；0关闭在环境中显式记录；不能仅凭模型名猜测。

    确定性采样batch-invariant + DEEPINFER_ENABLE_MTP_VARLEN=0 + 固定 seq_seed按README完整条件验证；不承诺跨任意硬件/软件版本位级相同。

    遇到的现象优先看哪里
    编译/导入失败平台环境变量、Python3.12、compiler/toolkit、torch/NCCL锁定版本、vendor gitlink、平台.so目录。
    Unsupported architecture/model_type/quantization是否用V4.1官方权重；仅有HF目录结构并不足够。核对config和quantization字段。
    CUDA无效设备 / 多进程使用错卡示例会重写可见设备；先看DEVICE_OFFSET、本机连续卡号、初始化顺序及调度器分配。
    多机挂住各节点版本和模型是否一致，节点RANK/WORLD_SIZE、MASTER_ADDR/PORT，所有DP/EP参与者是否到齐，通信和超节点拓扑。
    显存不足权重+冗余专家+KV/state+图捕获/激活总预算。不要把提高gpu_memory_utilization当万能解法；上下文/并发/并行策略一起评估。
    P已算完、D无法接续是否只是设置PROMPT/COMPLETION而没有实现钩子和传输；KV、SWA/state、token/采样/投机元数据及所有权必须成套处理。
    bench很快、真实服务不快满接受计数、排队/网络/KV/序列化、真实accept rate、LB、长尾与超时；使用线上有效token指标。

    建议把第一次实验的目标收敛为：在受支持硬件上，使用固定 V4.1 checkpoint 跑完官方离线示例并记录环境、rank配置与输出。在这条基线之前，不宜先搭复杂PD拓扑。
