01 / 先建立心智模型

SSH 不是“把密码换成文件”，而是两次不同的信任

主机信任：我连的是哪台服务器？

服务器有自己的 host key，例如 /etc/ssh/ssh_host_ed25519_key。客户端把主机名（也可能是哈希）、密钥类型与服务器公钥本体保存到 ~/.ssh/known_hosts；指纹是公钥的摘要，用来核对身份。第一次连接前应通过控制台、资产系统或管理员确认指纹，再接受。

用户认证：服务器允许哪个用户登录？

客户端用私钥签名，服务器用目标账号的 ~/.ssh/authorized_keys 中的公钥验证。私钥永远留在客户端；只复制公钥。

客户端先验证服务器身份，再由服务器验证登录用户的公钥。双向互信只是把这套关系在反方向再配置一次。

首次连接：从可信渠道核对 host key

SSH 传输层中，服务器用主机私钥签名密钥交换相关数据，客户端验证签名并检查该公钥是否属于目标主机。用户认证则签名包含会话标识符和认证请求的数据，并不是服务器随意发来一个“challenge 字符串”。

服务端控制台 / 已确认身份的管理通道：查看主机公钥指纹

sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

客户端：首次连接并人工核对同一密钥类型的 SHA256 指纹

ssh -o StrictHostKeyChecking=ask ops@server.example.com
# 核对与可信来源完全一致后才输入 yes；不一致就中止。
# 已保存的主机记录可以用 -F 查询；端口非 22 时使用 [host]:port。
ssh-keygen -F server.example.com
ssh-keygen -F '[server.example.com]:2222'

known_hosts 的结构示意（不是 shell；省略内容不是有效公钥）

server.example.com ssh-ed25519 AAAAC3...完整Base64公钥...
[server.example.com]:2222 ssh-ed25519 AAAAC3...完整Base64公钥...

若启用 HashKnownHosts，主机字段会是 |1|...，而非可读域名。ssh-keyscan 只能采集网络返回的候选公钥，不能证明其身份；必须与可信来源核对后才加入 known_hosts。authorized_keys 则是“可选限制字段 + 密钥类型 + 公钥 + 注释”，通常不含服务器域名。

最重要的区别：known_hosts 决定客户端是否相信“这台服务器”；authorized_keys 决定服务器是否允许“这个客户端密钥登录某个用户”。删除 known_hosts 不能修复公钥登录失败；删除 authorized_keys 也不能修复 host key 冲突。
02 / 安装、启动、端口与服务名

先让 sshd 稳定监听，再配置公钥登录

Debian/Ubuntu 通常使用 systemd 服务名 ssh；RHEL/CentOS/Fedora 通常使用 sshd。命令先在当前控制台或已有会话执行，避免关闭唯一管理通道。

# 安装服务端和客户端
sudo apt-get update
sudo apt-get install -y openssh-server openssh-client

# 启用并立即启动 sshd（服务名是 ssh）
sudo systemctl enable --now ssh

sudo systemctl status ssh --no-pager
sudo ss -lntp | grep -E ':(22|2222)\b' || true
sudo journalctl -u ssh -n 80 --no-pager
# 如果启用了 UFW：先允许 SSH
sudo ufw allow OpenSSH
sudo ufw status verbose

# 自定义端口时，先在防火墙放行，再改 sshd_config
# sudo ufw allow 2222/tcp
# 安装服务端和客户端
sudo dnf install -y openssh-server openssh-clients

# 启用并立即启动 sshd
sudo systemctl enable --now sshd

sudo systemctl status sshd --no-pager
sudo ss -lntp | grep -E ':(22|2222)\b' || true
sudo journalctl -u sshd -n 80 --no-pager
# firewalld：允许默认 SSH 服务
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --reload
sudo firewall-cmd --list-services

# 自定义端口 2222：先放行新端口，再修改监听配置；新会话验证前保留 22
# sudo firewall-cmd --permanent --add-port=2222/tcp
# sudo firewall-cmd --reload

Ubuntu 的 socket activation 与普通 ssh.service 不同

部分 Ubuntu 22.10+ 安装默认由 ssh.socket 持有监听 socket，来连接时再触发服务；镜像、升级路径与 Ubuntu 版本会影响实际行为。先检查状态，不要只凭“Ubuntu”判断。本文的 reload ssh 用于认证等 daemon 配置；在 socket 模式下，它不保证更改监听端口。

Ubuntu 服务端：只读识别实际监听方式

systemctl status ssh.socket ssh.service --no-pager
systemctl cat ssh.socket
systemctl show ssh.socket -p Listen -p ActiveState
sudo ss -lntp

若要改 Port/ListenAddress：普通服务模式先改 sshd 配置并校验，再 reload/按发行版文档重启服务；socket 模式还要按该版本的 Ubuntu 文档更新 socket 配置。带 sshd socket generator 的版本通常需 systemctl daemon-reload 重新生成，再重启对应 socket；旧版可能需显式配置 ssh.socket.d 的 ListenStream。保持控制台/旧连接，检查实际监听，再测试新端口。不要机械复制不同 Ubuntu 版本的端口迁移命令。

RHEL/Fedora：自定义端口还受 SELinux 约束

RHEL/Fedora 服务端：查策略，确认 2222 未被其他服务占用后再添加

sudo dnf install -y policycoreutils-python-utils
sudo semanage port -l | grep -E '^ssh_port_t|(^|[ ,])2222([ ,]|$)'
# 若 2222 不存在于任何其他服务的端口标签中，才执行：
sudo semanage port -a -t ssh_port_t -p tcp 2222
# 已经是 ssh_port_t 则无需重复添加；属于别的类型时先选另一端口或确认冲突。
# 回滚时只删除本次新添的规则，且先恢复并验证旧端口：
# sudo semanage port -d -t ssh_port_t -p tcp 2222

SELinux 端口标签、firewalld/UFW、安全组以及 sshd/socket 监听是独立条件。无需通过关闭 SELinux 解决端口策略；SELinux 不存在或 disabled 的系统不执行 semanage 步骤。

端口问题按层排查：进程是否监听 → 主机防火墙 → 云安全组/网络 ACL → 客户端路由。
远程变更原则：保持当前 SSH 会话，再开一个新会话验证；配置通过 sshd -t 后用 systemctl reload，不要先关闭唯一管理通道。
03 / sshd_config 与安全变更顺序

先备份，验证，再 reload

配置文件可能通过 Include 加载 drop-in；用 sshd -T 查看最终生效值。
OpenSSH 不是“最后一个配置覆盖前面”：对多数标量设置，先读取到的值生效。Include 位于主文件哪里、drop-in 按词法排序的位置、已有 cloud-init/vendor 配置、Match 条件都会影响结果。99-hardening.conf 不能默认覆盖 50-cloud-init.conf，也不能覆盖主文件中更早的值。少数可累计选项有不同语义，应查 sshd_config 手册。

服务端 shell：检查配置顺序并备份主文件 + 所有 drop-in

sudo grep -nE '^[[:space:]]*(Include|Match|PubkeyAuthentication|PasswordAuthentication|KbdInteractiveAuthentication|PermitRootLogin)' /etc/ssh/sshd_config
sudo find /etc/ssh/sshd_config.d -maxdepth 1 -type f -name '*.conf' -print 2>/dev/null
# 记下本次备份目录；以下变量仅在当前 shell 有效。
ssh_backup="/var/backups/ssh-guide-$(date +%Y%m%d-%H%M%S)-$$"
ssh_dropin=/etc/ssh/sshd_config.d/00-local-ssh-guide.conf
sudo install -d -m 700 "$ssh_backup"
sudo cp -a /etc/ssh/sshd_config "$ssh_backup/sshd_config"
if sudo test -d /etc/ssh/sshd_config.d; then
  sudo cp -a /etc/ssh/sshd_config.d "$ssh_backup/sshd_config.d"
fi
printf '备份目录：%s\n' "$ssh_backup"
sudo install -d -m 755 /etc/ssh/sshd_config.d
sudoedit "$ssh_dropin"

以下内容保存到上一步打开的文件。确认主文件在合适的全局位置有 Include /etc/ssh/sshd_config.d/*.conf；没有 Include 时，新文件不生效，应在备份后用 sudoedit /etc/ssh/sshd_config 有意识地配置。00- 仅帮助较早排序，仍必须验证有效值。示例要求已有可用的普通运维用户和 sudo 权限；若当前只靠 root 或 keyboard-interactive 登录，先完成迁移，再收紧对应配置。

配置文件内容：/etc/ssh/sshd_config.d/00-local-ssh-guide.conf（不是 shell）

PubkeyAuthentication yes
PasswordAuthentication yes
KbdInteractiveAuthentication no
PermitRootLogin no
MaxAuthTries 4
LoginGraceTime 30
# AllowGroups sshusers

服务端 shell：校验与有效配置，包含目标连接的 Match 条件

sudo /usr/sbin/sshd -t
# 将 user、host、addr、laddr、lport 换成实际连接信息。
# host 是客户端主机名，addr 是客户端地址，laddr/lport 是服务端地址/端口。
sudo /usr/sbin/sshd -T -C user=ops,host=client.example.com,addr=192.0.2.10,laddr=192.0.2.20,lport=22 | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin|maxauthtries|allowusers|allowgroups) '
# 仅选择本发行版的一个服务名；示例为 Debian/Ubuntu。
ssh_unit=ssh.service
# RHEL/Fedora 则把上一行改为：ssh_unit=sshd.service
sudo /usr/sbin/sshd -t && sudo systemctl reload "$ssh_unit"

sshd -t 成功只说明配置/密钥等基础检查通过，不证明账号、路由、PAM、Match、firewall 或公钥登录可用。必须保持旧连接并在另一终端重新登录。下面所有服务操作沿用已确认的 ssh_unit。

不要混淆的文件

sshd_config 是服务端；ssh_config 是客户端全局配置；~/.ssh/config 是客户端按 Host 匹配的连接配置；authorized_keys 是服务端目标用户允许的公钥。

验证有效配置

sshd -t 检查语法；sshd -T 输出综合后的值。Match 条件要用 sshd -T -C user=...,host=...,addr=... 核对。

04 / 生成密钥与理解文件权限

公钥可以复制，私钥不能复制

权限错误是公钥登录失败的高频原因：目标用户的 home、~/.ssh、authorized_keys不能被不可信用户写入。

客户端 shell：使用专用名称；已有文件时不覆盖

umask 077
install -d -m 700 ~/.ssh
ssh_key="$HOME/.ssh/id_ed25519_ops_guide"
if [ -e "$ssh_key" ] || [ -e "$ssh_key.pub" ]; then
  printf '该路径已有密钥文件，请核对后复用或另选名称：%s\n' "$ssh_key"
else
  ssh-keygen -t ed25519 -a 100 -f "$ssh_key" \
    -C "$(whoami)@$(hostname)-ops-guide"
fi
# 生成时交互输入 passphrase；不要为省事覆盖旧 key。
ssh-keygen -lf "$ssh_key.pub"
stat -c '%A %a %n' ~/.ssh "$ssh_key" "$ssh_key.pub"

上述 stat 是 GNU/Linux 语法，macOS 可用 stat -f。FIPS 环境可能不允许 Ed25519，应按当地策略使用 RSA 3072+ 和支持的签名算法。私钥口令保护磁盘上的私钥；它与远程账号密码不同。

客户端 shell：优先复用当前登录会话的 agent，解锁一小时

# SSH_AUTH_SOCK 已配置时复用现有 agent；没有时才启动。
if [ -z "${SSH_AUTH_SOCK:-}" ]; then
  eval "$(ssh-agent -s)"
fi
ssh-add -t 1h ~/.ssh/id_ed25519_ops_guide
ssh-add -l
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_ops_guide ops@server.example.com
# 已核对 host key 且 agent 已解锁后，验证脚本模式：
ssh -o BatchMode=yes -o IdentitiesOnly=yes \
  -i ~/.ssh/id_ed25519_ops_guide ops@server.example.com 'id -un'
BatchMode 不会自动解密私钥：BatchMode=yes 禁止密码、私钥口令和交互确认；首次 host key 未确认或加密 key 未在 agent 中解锁时，会失败。它用于“无人值守是否就绪”的验证。cron/systemd 不自动继承终端的 agent 环境；自动化应配置专用受限凭据或受控 agent 生命周期。不要默认开启 ForwardAgent；ProxyJump 通常不需要 agent 转发。
05 / 从单向登录到双向 SSH 互信

互信是“按用户、按方向、按主机”的双向公钥部署

双向互信不是“共享密码”，而是 A 的公钥进入 B 的授权文件，同时 B 的公钥进入 A 的授权文件。

推荐命令：先做 A → B，再做 B → A

分别在 A、B 的 ops 账号运行上一节的防覆盖密钥生成步骤，每台保留自己的 id_ed25519_ops_guide。接着按方向执行；每次首次连接先核对对方 host key。A、B 都必须安装服务端且 ops 账号已存在。

只在 Node A / ops 执行：部署 A 公钥并登录 B

ssh-copy-id -i ~/.ssh/id_ed25519_ops_guide.pub ops@node-b
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_ops_guide \
  ops@node-b 'hostname; id -un'

切换到 Node B / ops 后执行：部署 B 公钥并登录 A

ssh-copy-id -i ~/.ssh/id_ed25519_ops_guide.pub ops@node-a
ssh -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_ops_guide \
  ops@node-a 'hostname; id -un'
ssh-copy-id 的边界：它使用 SSH 连接并遵守 host key 检查，但不能替你确定首次看到的指纹是否可信。目标必须已有密码、已有密钥或控制台等可用的授权部署通道；它不能绕过认证。非默认端口可增加 -p 2222。

没有 ssh-copy-id 时：手工追加公钥

Node A / ops：只把公钥经 SSH 送到 B（避免重复执行造成重复行）

cat ~/.ssh/id_ed25519_ops_guide.pub | \
  ssh ops@node-b 'umask 077; install -d -m 700 ~/.ssh; cat >> ~/.ssh/authorized_keys; chmod 600 ~/.ssh/authorized_keys'

仅在 Node B 上，以管理员修复目标 ops 账号权限（按实际 home/group 调整）

sudo chown -R "ops:$(id -gn ops)" ~ops/.ssh
sudo chmod 700 ~ops/.ssh
sudo chmod 600 ~ops/.ssh/authorized_keys
# 仅有 SELinux 的系统执行；出错要查原因，不要吞掉错误。
# sudo restorecon -Rv ~ops/.ssh

手工追加不会自动去重，也不会给新账号创建 home。修复权限时先用 getent passwd ops、namei -l ~ops/.ssh/authorized_keys 确认目标路径和归属；不要对不明目录递归 chown。

06 / 多节点部署与互信模型

先决定你需要集中登录还是全互信网格

集中运维

控制节点公钥进入所有工作节点。工作节点之间不自动互信，适合管理员登录、发布和采集。

推荐默认

双向点对点

A 和 B 互加公钥，适合少量节点的作业调度或数据同步。

小规模

全互信网格

N 个节点每个都能登录其他 N-1 个节点，维护和撤销成本按方向快速增长。

谨慎使用
集中运维模式把控制节点公钥分发到目标节点；不等于节点之间可以互相登录。

Ansible：先满足引导登录，再分发公钥

前提：控制机可连接这些地址，已从可信来源建立每台主机的 known_hosts；远端已有 ops 用户、Python 3 和所需 sudo 权限。示例地址为文档保留地址，需要替换。安装 ansible-core 与 ansible.posix collection；下面展示密码引导（-k）与 sudo 密码（-K），也可以用你已有的 bootstrap 私钥替换 -k。

控制机 shell：建立独立 Ansible 环境

python3 -m venv .venv-ssh-guide
. .venv-ssh-guide/bin/activate
python3 -m pip install ansible-core
ansible-galaxy collection install ansible.posix

保存为 inventory.ini（INI 文件，不是 shell）

[workers]
node-01 ansible_host=192.0.2.11
node-02 ansible_host=192.0.2.12
node-03 ansible_host=192.0.2.13

[workers:vars]
ansible_user=ops
ansible_python_interpreter=/usr/bin/python3

保存为 ssh-keys.yml（YAML 文件，不是 shell）

---
- name: Deploy controller public key
  hosts: workers
  gather_facts: false
  become: true
  tasks:
    - name: Add public key without removing existing keys
      ansible.posix.authorized_key:
        user: ops
        state: present
        manage_dir: true
        exclusive: false
        key: "{{ lookup('ansible.builtin.file', lookup('ansible.builtin.env', 'HOME') + '/.ssh/id_ed25519_ops_guide.pub') }}"

控制机 shell：按顺序执行；-k/-K 会提示输入所需密码

# 先预览；确认目标和差异后再执行下一行。
ansible-playbook -i inventory.ini ssh-keys.yml -k -K --check --diff
ansible-playbook -i inventory.ini ssh-keys.yml -k -K
# 加密私钥先用 ssh-add 解锁，再验证 key 登录；不关闭 host key 检查。
ssh-add -t 1h ~/.ssh/id_ed25519_ops_guide
ansible workers -i inventory.ini -m ansible.builtin.command -a 'id -un' \
  --private-key ~/.ssh/id_ed25519_ops_guide \
  --ssh-common-args='-o IdentitiesOnly=yes -o BatchMode=yes'

密码引导是否需要 sshpass 取决于 ansible-core 版本/SSH 插件；若报缺失，可在 Debian/Ubuntu 控制机安装 sudo apt-get install sshpass，其他发行版按包管理器与仓库情况处理，或使用已有 bootstrap key。-k 是 SSH 密码，-K 是提权密码；已有免密 sudo 时可省略 -K。不要把密码写进公开 inventory。验证命令通过 inventory 的 ansible_host 连接，不要求 node-01 等别名在 DNS 中存在。

不要把私钥放进所有节点：全网共享一把私钥会让任意一台节点泄露后影响全部节点，也无法知道是哪台机器发起连接。服务账号应使用专用 key、命令限制和最小权限。
07 / 安全加固与可回滚变更

先让公钥登录成功，再关闭密码登录

配置项作用建议风险
PubkeyAuthentication启用公钥认证yes无公钥可用时不会自动修复账号问题
PasswordAuthentication密码认证确认公钥登录后改 no过早关闭可能锁住管理员
PermitRootLoginroot 直接登录通常 no；使用普通用户 + sudo救援场景需保留控制台方案
AllowUsers/AllowGroups限制主体明确列出运维账号拼错账号/组名会拒绝合法用户
MaxAuthTries单连接尝试次数4–6 起步agent中身份过多时需要 IdentitiesOnly
AllowTcpForwarding端口转发按业务需要限制关闭可能影响跳板/隧道

客户端新终端：确认仅公钥就能登录，不回退到密码

ssh -o PreferredAuthentications=publickey -o PasswordAuthentication=no \
  -o KbdInteractiveAuthentication=no -o IdentitiesOnly=yes \
  -i ~/.ssh/id_ed25519_ops_guide ops@server.example.com 'id -un; hostname'

确认成功后，服务端编辑第 03 节同一 drop-in，把下列三项调整为 no；不要追加到 shell 或随意创建另一个更晚的配置。若 PAM/AuthenticationMethods 要求多因素认证，应保留组织策略，并专门测试其组合。

修改现有 sshd 配置中的值（不是 shell）

PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no

服务端 shell：使用第 03 节确认的服务名，校验并重新加载

# Debian/Ubuntu：ssh_unit=ssh.service；RHEL/Fedora：ssh_unit=sshd.service
sudo /usr/sbin/sshd -t && sudo systemctl reload "$ssh_unit"
# 再用 sshd -T -C ... 检查实际用户连接的有效配置；随后新开连接验证。

回滚：恢复主文件，以及本次修改/新建的 drop-in

以下使用第 03 节保存的 ssh_backup、ssh_dropin 和 ssh_unit。若换了 shell，先从记录恢复这三个变量。只回滚本次指定文件，避免覆盖其他管理员的并发改动；若还编辑了其他文件，也应逐一从对应备份恢复。端口、SELinux、防火墙、socket unit 修改需要分别回滚。

服务端旧会话或控制台：检查备份后执行回滚

# :? 在变量未设置时直接报错，避免使用空路径。
: "${ssh_backup:?请设置第03节的实际备份目录}"
: "${ssh_dropin:?请设置本次drop-in绝对路径}"
: "${ssh_unit:?请设置本发行版服务名}"
# 固定目标文件名，避免误删其他配置。
if [ "$ssh_dropin" = /etc/ssh/sshd_config.d/00-local-ssh-guide.conf ] && \
   sudo test -f "$ssh_backup/sshd_config"; then
  if sudo cp -a "$ssh_backup/sshd_config" /etc/ssh/sshd_config && {
    if sudo test -f "$ssh_backup/sshd_config.d/00-local-ssh-guide.conf"; then
      sudo cp -a "$ssh_backup/sshd_config.d/00-local-ssh-guide.conf" "$ssh_dropin"
    else
      # 备份里不存在该文件，说明它是本次新建；回滚时移除。
      sudo rm -f -- "$ssh_dropin"
    fi
  }; then
    sudo /usr/sbin/sshd -t && sudo systemctl reload "$ssh_unit"
  else
    printf '恢复文件失败，停止 reload；请从控制台检查。\n'
  fi
else
  printf '目标路径或备份不匹配，停止回滚。\n'
fi

服务账号可以在 authorized_keys 行前加 from=、command=、no-agent-forwarding、no-port-forwarding、no-X11-forwarding。记录每把 key 的用途、负责人和轮换日期。

Host key verification failed

先确认服务器是否重装、IP是否复用或DNS是否指向新主机。确认无误后才用 ssh-keygen -R host 清除旧记录；不要长期使用 StrictHostKeyChecking=no。

Too many authentication failures

用 ssh-add -l 查看 agent；连接时加 IdentitiesOnly=yes -i key。必要时移除多余身份。

命令速查：连接与跳板

客户端 shell：连接命令

ssh -p 2222 -o IdentitiesOnly=yes -i ~/.ssh/id_ed25519_ops_guide ops@server.example.com
# 下方 config 保存并核对两台主机身份后：
ssh private-node
ssh -o BatchMode=yes private-node 'hostname; id -un'

客户端 ~/.ssh/config 内容：跳板和目标分别配置身份（不是 shell）

Host bastion
  HostName bastion.example.com
  User bastion_user
  IdentityFile ~/.ssh/id_ed25519_bastion
  IdentitiesOnly yes
  ForwardAgent no

Host private-node
  HostName 192.0.2.21
  User ops
  IdentityFile ~/.ssh/id_ed25519_ops_guide
  IdentitiesOnly yes
  ProxyJump bastion
  ForwardAgent no

跳板 key 是示例名称，需事先生成并部署；不要覆盖已有 key。ProxyJump 使用跳板提供 TCP 转发，目标 SSH 握手仍由本地客户端完成，必须分别验证跳板和目标 host key。跳板需要允许相应转发。配置保存后可执行 chmod 600 ~/.ssh/config；避免追加重复且冲突的 Host 块。
