1. 先把五个名字放对位置

名称与官方入口实际是什么维护状态与快照证据对 MI355X 的意义
AITERAI Tensor Engine for ROCm；多后端算子库、Python 接口与集成层活跃；最新发布 v0.1.25（10-12）；10-16 仍在更新 MI355 MLA kernel提供现成 attention、MoE、GEMM、norm 等 baseline，也适合把优化结果接回推理框架
CK / Composable KernelHIP/C++ 模板算子和组合组件工程活跃；代码迁入 rocm-libraries；CK 路径 10-15 有提交深入 C++ kernel、pipeline、MFMA 与数据搬运；已有大量算子实现
CK TileCK 工程中的 tile 编程体系；包括 include/ck_tile、example/ck_tile 等活跃；10-14 有 CK Tile 修复；不是一个独立版本库更显式地组合 tile、分布、pipeline、LDS 和寄存器布局
FlyDSLPython DSL + 独立 Fly dialect / MLIR 编译栈活跃；v0.4.0（10-14）；10-16 有依赖匹配修复显式 layout algebra、tiling、MFMA；有 gfx950 GEMM/MoE 测试与 MI35x CI
GluonTriton 内部的另一种 kernel 编程入口活跃；随 Triton 发布，稳定版 v3.8.0（08-28）；Gluon 10-16 仍有更新比普通 Triton 更显式地控制 layout、shared memory、异步操作；有 AMD CDNA4 API

CK 旧仓库的 Deprecated 不等于 CK 停止维护。 ROCm/composable_kernel 的说明已明确迁移到 rocm-libraries，旧 develop 为只读镜像。新贡献看 monorepo；AITER 仍通过旧地址固定 CK 子模块 commit，这是正常的版本锁定方式。

Gluon 不要单独 pip install gluon。 正确入口是 from triton.experimental import gluon，它也不是 MXNet 的 Gluon。

来源：AITER 快照、AITER 发布、FlyDSL 发布、Triton 发布。

2. 依赖图：它们不是一条串起来的链

图中的 AITER 后端是按算子与调用路径选择的，不意味着一次调用经过所有后端。CK Tile、Triton/Gluon、FlyDSL 也能独立写算子，不必经过 AITER。

关系是硬依赖吗？怎样理解
CK Tile → CK 工程同一源码工程不用再找一个独立 cktile wheel；版本跟随所选 CK commit
Gluon → Triton是，同包/同编译基础设施锁 Triton 发行物与 commit，就是锁 Gluon 的 API 与编译器
AITER → CK默认 CK 后端使用固定 submodule通常无需另装一个系统 CK；CK_DIR 覆盖才是主动替换依赖
AITER → FlyDSL当前 Linux 完整安装是必需依赖v0.1.25 与 main 的 pin 不同；旧资料中的 optional 已不能照搬
AITER → TritonTriton/Gluon 路径需要匹配版本当前安装脚本选择 AMD 构建，而非任意同号上游 wheel
FlyDSL → Triton/CK核心编译器不是以它们为后端设计借鉴不等于链接依赖；部分测试/复杂 kernel/baseline 可能用 AITER/Triton
FlyDSL → MLIR Python 包内嵌绑定wheel 自带 MLIR bindings；无需额外找通用 pip install mlir
CK → PyTorch独立 C++ 使用通常不需要Python 主要用于构建/代码生成；通过 AITER 接入时才涉及 PyTorch 集成

PyTorch 关系尤其容易误解：

  • AITER 的 Triton 安装脚本遇到 torch < 2.9.1 会跳过 Triton 替换，提示升级；这不是“任意 torch ≥2.9.1 都支持”。
  • v0.1.25 release workflow 默认设置 torch < 2.13，并记录 2.13 的 custom-op 名称处理兼容问题。这个上界是构建配置证据，也不是对整个区间的全面验证。
  • AITER_USE_SYSTEM_TRITON=1 只表示保留现有 Triton，不代表自动验证兼容。
  • setup.py 可能捕获 Triton 安装异常后继续；因此安装命令成功不等于目标算子已经可用。

证据：v0.1.25 requirements、v0.1.25 setup、main setup 快照、Triton 安装脚本、发布工作流。

3.2 CK / CK Tile：ROCm release tag、源码版本号、AITER pin 是三件事

场景应固定什么已观察到的要求
在 AITER 里修改/测试 CK 算子AITER 的 CK gitlink SHA不先升级到 CK develop；否则同时改变了两个变量
独立 CK，基底 ROCm 7.2.4monorepo rocm-7.2.4 tagCK 1.2.0；CMake 文件声明 ≥3.14，但 HIP 语言支持实际建议 ≥3.21；Python ≥3.8；默认 C++20
追踪 CK 新特性monorepo develop 的固定 SHA + 对应工具链本次快照 CK 1.3.0；CMake ≥3.21；Python ≥3.8；默认 C++20
参考当前新 SDK 构建查看所选版本 Dockerfile / TheRock 配置develop Dockerfile 已出现 Core SDK 10.1 默认值；不是继续沿用所有 7.2.4 条件

monorepo 同时有 rocm-7.2.4 与 therock-10.1 发布系列。不要把旧仓库显示的 7.2.4 当成整个生态的“最新版本”，也不要把 CK 的 1.2.0/1.3.0 当作 ROCm 版本号。

官方建议：非新特性开发场景，选择与已安装 ROCm 匹配的分支/版本。新的 SDK 配置并不自动证明某个旧编译器绝对不能构建；要以具体 tag 的构建与测试为准。

来源：CK monorepo、7.2.4 CMake、CK 当前源码安装指南。

3.3 FlyDSL / Gluon：不要混用 main 的代码与 stable 的编译器

项目可复现选择关键匹配点
独立 FlyDSL 实验flydsl==0.4.0 + FlyDSL v0.4.0 源码发布 wheel 为 Linux x86_64 CPython 3.10–3.14；例子/部分 kernels 不包含在 wheel 中
AITER v0.1.25 内的 FlyDSLflydsl==0.3.4.1遵循 AITER pin，不套用独立实验的 0.4.0
独立上游 Gluon 实验Triton v3.8.0 wheel + 同 tag 教程Gluon 在 experimental 命名空间，API 仍会变化

FlyDSL 源码编译 LLVMv0.4.0 锁 e2a39f504fee836e4def9581bed817ecc327b9dc + 该 tag 的补丁当前 main 即使 LLVM hash 相同，补丁集也可能变化

FlyDSL 当前 CI 观察到 ROCm 7.2.4 / Ubuntu 24.04 / Python 3.12 / PyTorch 2.10.0 镜像；这是一个 CI 配置事实，不是要求所有用户升级 PyTorch。10-16 的 FlyDSL 修复 正是在 CI 中运行 AITER 的 Triton 安装脚本，解决两者 API 不匹配。

Gluon 3.8.0 已有 CDNA4 mfma_scaled 等 API，但当前 main 的 scaled_downcast 等新接口不能假定稳定版也具备。NVIDIA TMA/WGMMA/tcgen05 教程也不能原样用于 MI355X。

来源：FlyDSL v0.4.0 README、FlyDSL LLVM pin、Gluon stable CDNA4、Triton LLVM pin。

4. 推荐基底：先把 ROCm / PyTorch / gfx950 对齐

候选复现基底：Ubuntu 24.04 + ROCm 7.2.4 + Python 3.12 + AMD PyTorch 2.9.1 容器。 AMD 固定版本文档列出了这个组合，本次也查询 Docker Hub 确认标签与 digest 存在。接上前述 AITER v0.1.25 pin 是有源码依据的安装配方，但还需要在你的机器做算子验收。

该 digest 对应标签 rocm7.2.4_ubuntu24.04_py3.12_pytorch_release_2.9.1。如果宿主机/镜像没有 render 组，按 /dev/dri/renderD* 的实际数字 GID 配置组权限。保留项目文件时，在 docker run 中另挂载自己的工作目录。

同一套环境至少核对这五层：宿主驱动支持 MI355X；容器/系统 ROCm userspace；ROCm 版 PyTorch；HIP 编译器支持 gfx950；AITER/DSL 依赖满足所选代码。驱动与 userspace 不必所有小版本逐字一致，但需要落在 AMD 支持的组合里。

torch.cuda 在 ROCm PyTorch 中仍是正常接口名。不要用 HSA_OVERRIDE_GFX_VERSION 把其他架构伪装成 gfx950 来绕过版本匹配。

来源：固定 ROCm 7.2.4 兼容矩阵、固定版本 PyTorch 安装说明、镜像标签。

5. 安装 AITER：算子开发优先源码模式

以下在独立开发容器中执行。安装脚本会替换 Triton 发行物；先固定基底，再固定 AITER，而不是在现有生产环境直接升级。

需要理解的细节：

  • 脚本把 ROCm 7.2.4 归到 rocm-7.2.0 的 AMD Triton 索引，这是它按 major.minor 选轮子的设计；不是要求把机器降成 7.2.0。
  • 它先清理 triton、pytorch-triton-rocm、triton-rocm、amd-triton 等同名模块发行物，再安装目标版本。安装后同时记录 distribution 名称、完整版本和 import 路径。
  • pip check 若提示 PyTorch 的 Triton 元数据依赖冲突，应记录并核对所选构建，不能用 pip install -U 一把覆盖回去。
  • 默认 PREBUILD_KERNELS=0；算子首次调用可能 JIT。先验收少量目标算子，不一开始预编译所有后端和架构。
  • RMSNorm 测试的命令行参数已按 v0.1.25 源码核对；通过它只能说明这条算子路径可用，不代表 GEMM/MoE/attention 全覆盖。

若缺 CK 子模块，在 AITER 根目录运行 git submodule update --init --recursive。不要执行 git submodule update --remote 把固定依赖追到最新。

只使用预编译库时，可取 v0.1.25 发布资产。包名是 amd-aiter，导入名是 aiter。例如本基底应选 ROCm7.2 + cp312 + x86_64 的 wheel：

注意三个不同的变量语境：

  • AITER 常用 GPU_ARCHS=gfx950 环境变量。
  • CK 例子/测试用 CMake -DGPU_TARGETS=gfx950。
  • CK 自己的 GPU_ARCHS 构建路径有不同语义；当前源码指南指出它用于跨架构族库构建，会清空 GPU_TARGETS 并跳过例子/测试。不要把 AITER 的配置直接照抄成 CK 参数。

典型阅读入口：include/ck_tile/core/ → include/ck_tile/ops/ → example/ck_tile/03_gemm/。旧 CK 的 device operator/instance 体系与 CK Tile 共存；“Tile 更新”不意味着旧实现完全失去价值。

9. MI355X 优化时，选哪条开发路线？

你的目标首选起点要观察什么
先让服务或模型快起来AITER 现成 kernel 与 dispatch是否选中预期后端、shape 覆盖、layout/量化转换成本、端到端调用开销
C++ 深度优化 GEMM/attention pipelineCK Tile；对照已有 CK/ASM baselineMFMA 指令、tile 大小、流水级数、LDS swizzle、寄存器压力
Python 快速验证融合/布局想法先有 Triton baseline，再比较 Gluon/FlyDSLfusion 收益、layout 转换、访存合并、async copy、编译时间
显式控制 Triton 生态里的线程/数据布局GluonBlockedLayout/AMDMFMALayout、shared memory、CDNA4 intrinsic
实验 layout algebra / tile compositionFlyDSLshape/stride、partition、copy/MFMA atom、MLIR lowering
修改后端 codegen / ISA 生成对应项目的固定编译器源码LLVM pin、补丁、生成 ISA 与 register allocation

不要预先认定“某 DSL 一定更快”。先固定 shape、dtype、stride、layout、量化 scale 格式、精度阈值、batch 分布、调用方式，再比较同一工作负载。AITER 在这里既可以是最终集成入口，也可以是性能对照组。

MI355X 常见词如何理解调优时怎么用
gfx950 / CDNA4编译目标标识 / GPU 架构代际所有 kernel、编译器与设备信息必须一致；不能沿用 gfx942 假设
WavefrontAMD 的执行线程组；MI355X 常用 wave64不把 CUDA warp32 的 layout 公式直接搬来
MFMAAMD 矩阵乘加指令检查生成的指令形状、dtype、数据布局是否匹配期望
LDS / Swizzle片上共享存储 / 地址重排降低 bank conflict，安排异步搬运与双缓冲
VGPR / AGPR / Occupancy寄存器资源 / 驻留工作量tile 更大可能提高复用，也可能寄存器过多导致 occupancy 下降或 spill
OCP FP8 / FNUZ / MXFP4不同数值/缩放表示核对真实 dtype、scale 粒度、scale layout、packing；同为 8-bit 不等价
Preshuffle把权重预排成 kernel 喜欢的布局单看 kernel 可能快，但要交代重排成本与是否可摊销
Split-K将 K 维拆给多个工作单元并做合并小 M/N、大 K 时可能增加并行，也会增加 reduction 与额外流量
JIT / Autotune cache首次编译与配置搜索结果缓存分开冷启动与稳态；改编译器/版本后不要误用旧缓存作为结论
Roofline理论算力与可用带宽形成的性能上限先判 compute-bound 还是 memory-bound，再选优化方向

10. 验收、排障与复现清单

按顺序做四层验收：能发现 GPU → 能导入库 → 能编译并通过目标算子正确性 → 在真实 shape 分布上改善性能。任何前一层通过，都不能代替后一层。

症状先检查
no kernel image / invalid device function实际 target 是否 gfx950；wheel/code object 是否含 gfx950；编译器是否支持
找不到 Gluon APITriton 的完整版本、发行源和源码 SHA；是否把 main 代码配了 stable wheel
import triton 路径奇怪是否同时安装 triton / pytorch-triton-rocm 等，或 cwd/PYTHONPATH 遮蔽
