01

硬件层级，与任务层级。

SM 是执行硬件；CTA 和 warp 是程序的组织单位。一个 CTA 在一个 SM 上执行，2CTA 模式让两个 CTA 分别驻留在两个 SM 上协作。

HARDWARE / 硬件资源

GPU → SM → 执行管线与存储

Tensor 管线普通算术 / load-store寄存器SMEMTMEM

完整硬件还有 die、GPC、TPC 等层级。这里聚焦 SM 内部：SM 同时拥有多种执行资源，Tensor 管线是其中负责矩阵运算的一部分。

SOFTWARE / 工作组织

Grid → cluster → CTA → warp → thread

1 warp = 32 threads当前 down：1 CTA = 8 warps1 cluster = 2 CTAs

cluster 是可选的协作组；不是每个算子都使用它。worker 通常是软件中的任务角色或工作进程，不是 CUDA 的固定硬件层级。

MMA = Matrix Multiply-Accumulate。数学上是 D = A × B + C。Blackwell 的 tcgen05 路径由被选中的线程发起异步指令，Tensor 管线执行矩阵乘加并更新 TMEM；普通线程仍负责地址、同步、scale 和 epilogue。不能把 Hopper 的 4-warp WGMMA 发射规则直接套过来。
02

存储在哪里，谁负责搬运。

TMA 是搬运机制，HBM、L2、SMEM、TMEM 是不同的存储层。寄存器连接计算结果和普通线程执行的 epilogue。

图中层级表示数据依赖，不代表按比例绘制的带宽或延迟。FP8 输入 scale 还涉及 SMEM → TMEM 的专用处理，不能与输出累加器读回混淆。

名词解读速度怎样比较
HBMGPU外部高带宽显存，承载global内存。看整卡带宽与实际读写量；不同型号峰值不同。
L2多个SM共享的片上缓存；global访问可命中这里。通常比访问HBM更近；命中率、访问模式和争用决定收益。
TMATensor Memory Accelerator；异步块搬运、描述符与多播机制。没有一个独立的“TMA显存速度”；由源数据层级、传输尺寸、请求数和流水决定。
SMEMCTA使用的片上共享内存，容纳输入切片与输出暂存。关注bank冲突、布局和并发访问；不能直接把每SM带宽与整卡HBM峰值比较。
TMEMBlackwell Tensor Memory，承载MMA累加器及相关Tensor数据。用专用指令访问；容量、布局、load/store吞吐和同步影响读回。

不能用一个统一的 GB/s 数字描述整条链。计算、搬运能够重叠；DRAM利用率较低可能是数据已经搬完，也可能是缓存命中、任务太少或等待同步，需要结合时间线判定。

DESIGN / 怎样分工

按瓶颈配置线程，不能平均分配

Tensor管线执行乘加，更多warp只负责发射并不自动提升吞吐。先确认搬运是否供得上，再检查scale、TMEM读回、量化和写出。

当前down的epilogue需要BF16舍入、group32求scale、FP8转换和packed scale写出；这些操作由普通线程执行。

空闲warp也不能直接改岗位。增加epilogue线程会改变barrier人数、数据分配和资源占用，必须一起修改并验证。

为什么只计算一轮时，气泡占比更高？

首片搬运无法被前一轮MMA掩盖，最终epilogue也没有后一轮计算去覆盖。只有一轮时，这些固定开销在总时间中占比更高。

“占比更高”不等于空闲的绝对时间一定最长。多轮工作也可能遭遇中途等待；若有多个输出tile，持久CTA还可能重叠不同tile的计算与输出。

流水不等于每轮搬出累加器

默认56轮，输入A/B切片搬入56轮、MMA不断更新同一份TMEM结果。最后完整读回一次，再做BF16舍入与FP8量化。

完整读回包含多条load指令；每个BK128包含4次K32 MMA；12 stages不是12轮计算，更不是先把12片全部搬完才开算。

教学模型的时间不等于nsys trace。动画用任意“模型节拍”演示依赖：TMA每节拍最多发起一片，片的搬运延迟可调，MMA串行消费，结束后用固定8节拍表示读回与epilogue。省略scale转置、cluster barrier、带宽争用、指令开销及输出分条重叠；不能用于预测真实GPU时延或选定最优stage。
06

更多 stages，换来什么，也占掉什么。

stage是输入缓冲槽。更多槽允许预取更远的K片，也占用更多SMEM。驻留CTA指已经获得SM资源、线程和缓冲尚未释放的thread block。

固定M30配置的SMEM预算

0半个SM：114KiB每SM上限：228KiB
225KiB / CTA
1只按SMEM计算能装几份

估算采用该快照的内存布局：固定8192+52B；每stage为A 1024B + B 16384B + scale 1024B + barrier 24B；总量按1KiB对齐。

在教学模型中，收益会饱和

(S − 1) × Tconsume ≳ Lload
S ≳ 1 + ceil(Lload / Tconsume)

这只是稳定流水的起始估计：槽位释放、发射吞吐、scale和同步会影响真实预取深度。S个槽通常允许大约S−1片领先当前消费者，不保证始终满载。

本实现还有TMEM约束。当前kernel明确假定同一SM不同时容纳两个使用该TMEM布局的CTA，并检查TMEM分配起点为0。减少stage到“SMEM装得下两份”，不等于代码已经安全支持双CTA驻留。寄存器、线程槽、TMEM和实现限制还要共同满足。

少stage

内存少，但预取太浅时MMA可能等数据；不能仅看资源变少就断言更快。

够用的stage

搬运等待被掩盖；计算持续推进。再增加槽位，收益可能已经很小。

太多stage

更大的SMEM footprint，可能削弱驻留能力；若超过容量则配置不可用。

真实最优stage需要固定BM/BN/BK、cluster和线程分工，用同批Graph/L2 flush计时及精度门禁比较候选。当前页面的“饱和点”只属于可调教学模型。

07

splitK：先保存部分和，再合并。

splitK让不同CTA负责不同K区间。它增加可并行任务，同时引入部分和存储、规约和数值顺序变化。当前M30 latent down的splitK为1。

点击演示：部分和写出 → 可见性与完成通知 → 规约 → 最终输出。

最后完成的CTA合并

示例Indexer先把FP32 partial写入global scratch，执行可见性同步，再更新完成计数。最后完成的CTA从global读取所有分段，按确定顺序在寄存器里求和。

负责合并的物理SM不是预先指定的。CUDA决定CTA在哪个SM上运行；“最后完成”由计数协议判断。

独立kernel合并

生产kernel结束前保存部分和，随后规约kernel读取scratch。它可以直接global → registers，也可以额外用SMEM做局部规约。

新kernel不能继承已经退出CTA的TMEM；通常不存在把任意SM的TMEM直接聚拢到另一个SM寄存器的流程。

global地址不等于每次都访问HBM。partial读取可能命中L2。要保持数值契约，还需控制K分段、段内累加、段间求和与舍入位置；如果每段先量化再求和，通常与合并FP32后最终量化不同。
08

2CTA协作：共享输入，不切K。

两个CTA处理相邻输出列，使用相同的激活行。每个CTA搬一半A切片，配合2-SM MMA完成更宽的输出。

这里的A是什么？

Y = A × B
A = x[M,K]，B = Wᵀ[K,N]

swap_ab改变硬件操作数方向；上面的逻辑A仍指输入激活。当前2CTA单轮合起来计算逻辑16×256，两个CTA各输出16×128。

减少A缓冲，有什么代价？

好处是激活复用和每CTA的A缓冲降低。代价包括cluster同步、两个SM的联合调度和更少的独立调度灵活性。

上述字节只计算原始A切片；不是整个算子的HBM流量，也不意味着时延减半。2CTA更不是splitK=2。

09

BM、BN、BK，怎样选。

BM/BN定义输出tile，BK定义一轮消费的K切片。tile越大，复用可能越好，但任务数、padding和片上资源也随之改变。

参数定义增大后的收益可能的代价
BM每CTA输出行数权重复用更高M方向任务减少，尾部无效行、寄存器和TMEM需求增加
BN每CTA输出列数激活复用更高N方向任务减少，累加器和输出处理增加
BK每轮K长度循环与同步次数减少每stage输入更大，可能压缩可用stage数量，受scale与指令约束
M30的实际取舍。BN128下，BM16产生56个输出CTA；BM32只产生28个。两者都把M填充到32行，BM32没有减少这部分padding，却把并行任务数减半。上方切分控件可以直接看到这一点。

10

把容易混淆的词，放在一起。

SM

Streaming Multiprocessor。执行CTA的硬件单元，含普通计算、Tensor管线及片上资源。

CTA / Block

Cooperative Thread Array。线程块；本页down每CTA 256线程。它在一个SM上执行。

warp

32个线程组成的执行组。程序可分配加载、MMA发射、scale、输出等不同角色。

cluster

多个CTA的协作组。这里是两个CTA、两个SM；不是一个CTA跨两个SM。

worker

软件角色名，可指CPU工作进程、GPU工作任务或持久调度角色；不是固定硬件单位。

MMA

Matrix Multiply-Accumulate，矩阵乘加。当前tcgen05路径把累加器保存在TMEM。

stages

输入流水线可复用缓冲槽数，影响预取深度与资源容量；不是计算轮数。

splitK

把K方向拆给多个CTA，各自求部分和，然后按协议规约。与2CTA共享输入不同。

epilogue

完整累加之后的输出处理，例如舍入、sigmoid、残差、门控、量化和写出。

怎样读资源指标

指标能说明什么不应该怎样解读
SM覆盖上界输出任务数对SM预算的几何约束；M30示例56/148≈37.8%。不是实测SM Active，也不是精确调度占用率。
SM Active特定采样/计数口径下SM处于活动状态的比例。活动不等于所有管线满载；不能只按100%判断好坏。
Tensor ActiveTensor资源活动情况，需核对采样范围和计数定义。不是MFU；少CTA、准备/输出阶段、同步等待都可能使它低。
DRAM读HBM侧实际读活动/吞吐，受缓存与重叠影响。低值不能单独证明“搬运已完成”；也可能是缓存命中、工作量小或等待。
核间空隙同一统计区间内多个GPU kernel之间的间隔。一个严格单kernel没有“kernel之间”的gap；复合算子、Graph、回放或阶段kernel会有，kernel内部等待是另一回事。
理想情况下，所有利用率都应该100%吗？

不应该。计算受限任务通常希望Tensor计算持续推进；带宽受限任务希望数据供给接近可达吞吐。小矩阵可能先受任务数和固定开销约束。优先看目标时延和精度，再用同一口径的资源指标解释瓶颈。

为什么把epilogue融合进来，还会有收尾气泡？

融合避免了额外kernel启动及中间global结果，但epilogue仍需等待完整累加，再执行读回、舍入、量化和写出。一个tile只有一轮K时固定开销占比更高；多tile持久调度才可能创造跨tile重叠。

这些动画能判断哪份kernel更快吗？

不能。它们用于解释切分、依赖、缓冲复用和规约位置。真实选择需要精度验证和一致计时条件；采样指标不能替代Graph/L2 flush benchmark，源码推导不能替代GPU执行证据。
