01 / 先建立计算模型

M/N 决定输出块，K 决定每块要累加多少次

逻辑上 A[M,K] × B[K,N] → C[M,N]。你的路径使用 FP8 A/W 与 FP32 scales，物理权重为 W[N,K]，数学上的 B=Wᵀ；preshuffle 后的权重字节序还会按 kernel 要求重新排列，不能直接当普通转置矩阵解释。

C[m,n] = Σₖ A[m,k] × B[k,n]
blockscale：C[m,n] ≈ Σg sA[m,g] × sW[⌊n/128⌋,g] × Σ(k∈g) AQ[m,k] × WQ[n,k]
层级切什么在做什么
Grid / workgroupM、N 按 BM、BN 分块一个 workgroup 通常负责一个 BM×BN 输出 tile；多个 workgroup 并行。
K 循环K 按 BK 分段同一 workgroup 反复读取 BM×BK 的 A 与 BK×BN 的 B，累加到相同的输出 tile。
128 blockscaleK 按 128 划 scale 组；W 还按 N=128 分组每段 dot 使用对应的 A/W scale；scale 随 K 变化，不能把整个缩放统一推迟到最终 epilogue。
Wave / MFMA输出 tile 再拆成 wave 子块与指令小块一个 wave 的 64 个 lane 协同执行矩阵指令，fragment 分散在 lane 的寄存器里。
Split-K（算法选项）把 K 的不同区间分给多个 workgroup需要对应实现支持。已核查的 CK/CK Tile preshuffle tuner 不启用此轴；通用图可用来理解其他实现。
BK、scale block K=128、Split-K 是三个不同概念。BK 变小通常只增加 block 内循环，不增加普通 GEMM 的 grid；跨多个 scale 组的 BK 必须正确处理各组独立缩放。128 粒度也不表示允许任意 BK。

目标内核 · FP8 A8W8 + B preshuffle + 128 blockscale

这条路径里，B 直接进入寄存器；每个 K=128 缩放段独立乘 scale

以 AITER v0.1.25 固定 CK 版本的 WPABQuantBPipelineAgBgCrV2 4-wave 路径为例。逻辑输入是 A[M,K] 与 W[N,K]，输出 C=A·Wᵀ。B=Wᵀ 是数学视图；preshuffle 是另一层物理存储重排。

缩放合同：sA.shape = [M, ceil(K/128)]；sW.shape = [ceil(N/128), ceil(K/128)]。A 每行每 128 个 K 元素共用一个 scale，W 每 128×128 个 N/K 元素共用一个 scale。128 是量化分组大小，与 block tile、wave 数、MFMA 的 K 宽度是不同参数。

BK 与 scale 的正确关系：数学上 BK32/64 可分别用 4/2 个小块凑成一个 K128 缩放段；BK256 内含两个不同 scale 段，必须分段乘 scale。当前这条 CKTile 路径要求 BK≥128 且满足指令/分组整除条件；AITER v0.1.25 的 gfx950 Triton blockscale wrapper 还要求 BK=GROUP_K=128。因此不能把 BK32/64 当成这些接口直接支持的 sweep 候选。

LDS 粗估只算 A：FP8 的 A 双缓冲约为 2×BM×BK bytes；BM128/BK128 时为 32 KiB。这还没计入 LDS padding、epilogue/C-shuffle 等资源。实际驻留能力应以编译的 group_segment_fixed_size、VGPR/AGPR、scratch、occupancy 报告为准。

省下 B LDS 不等于省下所有资源：B 的预取/ping-pong fragments、A 中转寄存器、scale 寄存器、FP32 分段部分和与总 accumulator 都可能增加寄存器压力。源码同时存在部分和与总和；编译器能否复用，以及实际 VGPR/AGPR 数量，必须看生成代码。8-wave 特化使用另一套 pipeline，不能复用本图的资源公式。

FP32 scale 与 E8M0 是两条合同：这里展示 FP32 blockscale。gfx950 的 FlyDSL MX 路径可以把 E8M0 缩放直接送入 scaled MFMA，128 分组通过广播适配硬件 32 元素子组；它要求对应的 scale preshuffle。不要为切换 kernel 擅自将任意 FP32 scale 舍入成 E8M0，也不要用 per-row/per-column epilogue scaling 代替沿 K 改变的 blockscale。

04 / workgroup 继续拆成 wave 与指令

一个 CU 不等于一个 tile，一条 MFMA 也不等于整个 GEMM

当前选择的 BM×BN 输出 tile，示意分成 WM×WN 个 wave 子块。不同 kernel 可采用不同分布。

固定 FP8 例子：128×128×128

  • 4 waves × 64 lanes = 256 threads / workgroup。
  • 若 wave grid 为 2×2，则每 wave 负责逻辑上 64×64 的 C 子块。
  • 以一种 16×16×128 FP8 warp-GEMM 逻辑 tile 为例，每 wave 的一个 BK=128 步需要 (64/16)×(64/16)×(128/128)=16 次逻辑 warp-GEMM，之后应用对应的 blockscales。
  • 64×64 / 64 = 平均每 lane 64 个 FP32 输出累加元素；不是“每 lane 固定连续 8×8”，真实 fragment 映射由指令布局决定。
  • 该 blockscale 路径还有分组临时 acc 与总 acc，另有 A/B fragments、scales、地址和流水线状态。64 个数学输出值不能当成真实寄存器数。

固定 AITER/CK 实例中也有 16×16×64 的 warp tile；具体展开成多少条 ISA 以编译后反汇编为准，对一个 128-K scale 组需要更多 K 方向重复。指令选择与 block tile、量化分组是三个层级；具体合法性看目标实例和生成代码。

1. 先固定算子的数学含义和内存布局

对象逻辑形状 / 含义实际接口要求
A / XQ[M,K]，每个 token 的输入gfx950 的 aiter.dtypes.fp8 对应 torch.float8_e4m3fn；不是 INT8，也不是 gfx942 的 E4M3 FNUZ。
W / WQ[N,K]，计算 Y=A×Wᵀ；数学中的 B 为 [K,N]先做 shuffle_weight(WQ, layout=(16,16))。返回 tensor 的 shape 仍是 [N,K]，但字节已经重新排列。
A scale[M,ceil(K/128)]；每行、每 128 个 K 元素共享一个 scale普通 preshuffle 公共入口使用列优先的 scale 字节布局。官方 tuner 用 sa.T.contiguous().view(*sa.shape)，形状仍不变。
W scale[ceil(N/128),ceil(K/128)]；W 的每个 128×128 块共享一个 scale普通 FP32 scale 路径保留这一 scale 表；不要因为 W 被 shuffle 就自行对 scale 套用相同排列。
输出[M,N]公共接口支持 BF16 / FP16；本目标 tuner 的参考输出为 BF16。

令 g 表示 K 上的第 g 个 128 元素分组，计算关系为：

Y[m,n] = Σ_g { sA[m,g] × sW[floor(n/128),g]
                    × Σ_{k ∈ group(g)} Aq[m,k] × Wq[n,k] }

scale 随 K 分组变化，不能把所有 K 的裸 FP8 乘积累加完成后，只乘一个总 scale。量化分组 128 与 BK 不是同一个概念：CK Tile 候选中存在 BK=256，一个 tile 会覆盖两个量化分组；当前 AITER Triton harness 则要求该 family 的 BK=128。

2. B-preshuffle 究竟做了什么

对 1-byte FP8 和 layout=(16,16)，官方实现把 W 的局部 16 行 × 32 列重新排列，为 wave / MFMA 消费顺序准备数据。简化为单矩阵的等价变换：

# Wq: [N,K], FP8，已经完成量化
# 省略源码中的批次维；这是排列解释，不是另一个量化步骤
Wq.view(N//16, 16, K//32, 2, 16) \
  .permute(0, 2, 3, 1, 4) \
  .contiguous().view(N, K)

shuffle_weight 本身要求 N%16=0、K%32=0；目标 kernel 还可能有更严格的 tile / quantization 约束。首轮建议用 N、K 均为 128 的倍数，尾部单独验证。它不是转置，也不改变 scale 或数值；逻辑上相同的数据使用了不同地址映射。

import torch
import aiter
from aiter.ops.shuffle import shuffle_weight

# 已有 Aq[M,K]、Wq[N,K]，dtype=torch.float8_e4m3fn
# 已有 FP32 sa[M,K//128]、sw[N//128,K//128]
# 此例仅示范 N、K 对齐到128的输入合同，不包含量化过程
Wq_shuffled = shuffle_weight(Wq, layout=(16,16))
sa_column_bytes = sa.T.contiguous().view(*sa.shape)
Y = aiter.gemm_a8w8_blockscale_bpreshuffle(
    Aq, Wq_shuffled, sa_column_bytes, sw,
    dtype=torch.bfloat16,
)
最容易出现“快但算错”的地方：shape 与 stride 不能完整说明这些 buffer 的含义。W 的 shape 没变，scale 的 shape 也可能没变，但字节顺序已改变。量化器若已经输出转置 scale，就不能再转一次；不同 kernel 的 AQRowMajor 选项也必须与输入合同一起改。正确性测试应使用原始 W、原始逻辑 scale 反量化建立参考。

FP8 专项 / 让完整调用路径变快

128 scale block 如何约束 BK

用 A ≈ A8 × sA、B ≈ B8 × sB 表示反量化 scale。示例中 sA 的逻辑形状是 [M, ceil(K/128)]，sB 的逻辑形状是 [ceil(K/128), ceil(N/128)]；物理存储可能转置或预排。对输出元素：

C[m,n] ≈ Σg { sA[m,g] × sB[g, floor(n/128)]
                 × Σ(k 属于第 g 个 128-K 区间) A8[m,k] × B8[k,n] }

这里的 sA/sB 是反量化乘数。
如果接口存储 reciprocal scale，加载后必须按该接口约定使用。
BK 候选与 128-K scale 的关系搜索价值合法性与数值检查
BK=64（仅数学对照）通常两次 K tile 覆盖一个 scale block较小缓冲、更细流水；可复用同一段 scale当前已核查的 CK Tile 路径不支持；若另写实现，必须验证半组部分和与缩放
BK=128与一个 scale block 对齐最清晰的初始基线，scale 边界与主循环一致仍需检查 MFMA、LDS、packed B 和编译器约束；并不保证最快
BK=256一次覆盖两个不同的 K scale block可能减少控制开销、扩大搬运和计算重叠窗口必须保留两段各自的 partial 与 scale 语义；不能对整段 256 的 dot 只乘一个 scale

若 BN=256，在此示例 scale 几何下同一输出 tile 跨两个 N scale 区块；每个输出列必须使用对应 scale。BN=64 则可能有相邻 tile 共享一个 N scale 区块。BM 的 scale 复用取决于 A 是逐行还是二维 blockscale，不能只凭“blockscale=128”推断。

核心错误模式：跨多个 K scale block 先把未经缩放的 FP8 dot 全部累加，再统一乘一个 scale，通常不等价于 blockscaled GEMM。一个 candidate 编译成功并不表示 scale 语义正确；BK、split-K 和 K-tail 都要专门验证。

正确性、计时与结果归档

先回答“在测哪段时间”

口径应该包含适合回答
单 kernel该 GPU kernel 的执行；排除 JIT、分配与拷贝内核改动有没有改善？

一套可靠的微基准流程

  • 固定环境：记录 GPU/分区、gfx、CU 数、驱动、ROCm、编译器、库 commit、容器镜像及共享负载；观测温度/频率/功耗，避免不同热状态偏置结果。
  • 编译与预热分离：先完成编译、输入和 workspace 分配。可从 20–100 次预热开始，再依据 kernel 时长与热稳定情况调整；不把首个 JIT 算进稳态延迟。
  • 使用 GPU event：在同一 stream 记录计时事件并同步结束事件。ROCm PyTorch 仍使用 torch.cuda.Event、torch.cuda.synchronize 这些 API 名称。
  • 让每轮计时足够长：一轮运行多次 launch，例如累计 20–100 ms，再除以次数。先做约 10–30 轮，交错或随机化候选顺序，报告中位数和离散程度；具体次数按噪声调整。
  • 区分普通 launch 与图捕获：短 kernel 可能受 CPU 供给影响。图捕获能降低这类开销，但必须与目标部署模式一致；两种结果分别记录。
  • 区分缓存模型：重复同一输入、轮换输入、权重长期复用等对应不同工作负载。用真实访问模式选择热/冷缓存口径，不将热缓存结果解释为持续 HBM 带宽。
  • 短名单独立复测：多做几个独立批次；在 profiler 之外重新计时。若收益落在测量波动内，先增加证据，再决定是否更换内核。
不要制造虚假的精度。10 次样本不足以可靠报告 p99；“一轮许多 launch 的平均时延”的分布也不是线上单请求尾延迟。HTML 中的 tile 分解、FLOPs 和填充比例可以计算，微秒、TFLOP/s 和 speedup 必须来自实测。

正确性是一项约束，不是最后的勾选框

为每种 dtype/累加路径定义参考结果和容限。常见逐点契约是 abs(out − ref) ≤ atol + rtol × abs(ref)；同时记录最大绝对误差、明确 epsilon 约定的相对误差、相对 L2 误差，以及 NaN/Inf。可信库可以作为参考，但参考的精度与计算路径也要写清。

  • 测试零值、正负混合、正常随机输入、不同量级、抵消，以及真实数据分布。
  • 覆盖边界 M/N/K、非整齐维度、不同合法 stride、地址偏移和对齐；只测整齐 shape 会漏掉 tail/mask 错误。
  • split-K 改变加法次序，可能改变误差；atomic reduction 可能非确定。若业务要求确定性，应明确排除不满足要求的路径。
  • FP8/FP4 需验证 scale 布局、转换、饱和及整体精度；若量化在线执行，必须纳入正确性和整体算子耗时。

怎样决定是否采用赢家

保留 top-k，在独立批次中复测。不要挑“最快的单次”作为结论；优先考虑收益稳定、workspace 可接受、精度通过、邻近 shape 不显著退化的候选。性能相近时，较低方差、较少资源占用和较小维护成本更有价值。
