01 / 先澄清“tile 单元”

Tile 是计算分块；SM 才是承载线程块的硬件单元

讨论算子时，tile 通常指 BM×BN 输出块、BK 长度的 K 段，或一条矩阵操作的逻辑形状。它是程序的分工方式，不是芯片上固定数量的一排“tile 核”。你想问的硬件规模，最接近 SM 数量和每 SM 的 Tensor Core 数量。

GPU / package一颗 CUDA 可见设备。B200 由两个 die 协同组成一颗 GPU。
SMStreaming Multiprocessor；容纳 warps、寄存器、shared memory 和计算单元。
Tensor CoreSM 内的专用矩阵运算硬件。程序发出 MMA 类指令，通常不指定第几个物理 Tensor Core。
软件 tile程序选择的数据块；同一硬件运行不同 BM/BN/BK 会得到不同任务数量。
MI355X 中的概念NVIDIA 中的对应概念不能直接照搬的地方
CUSM职责相近；内部执行资源、指令、峰值与存储大小不同，不能按个数直接比较算力。
Wave64Warp324 个 waves 是 256 threads；4 个 warps 是 128 threads。
WorkgroupThread block / CTA普通 CTA 的全部 warps 在一个 SM 上；不同 CTA 的 shared memory 默认独立。
LDSShared memory / SMEM都是显式管理的片上协作存储；bank、swizzle、同步、容量与搬运机制不同。
MFMAMMA / WGMMA / tcgen05.mma调用与协作粒度、fragment 布局和 accumulator 存储位置不同。
无简单一对一项Thread-block cluster / TMEMcluster 是多个 CTA 的协作层；B200 TMEM 是 Tensor Core 专用存储，不能当普通 shared memory 使用。

再补两个硬件层级：GPC 与 TPC

GPC 是芯片内更大的处理组织，包含多个 TPC；TPC继续组织SM。Hopper典型TPC包含2个SM，但产品会屏蔽部分资源，不能仅用SM总数反推出有效GPC/TPC布局。本页不给未核实的H20/B200 GPC数量。

硬件：GPU package → die → GPC → TPC → SM → 矩阵/向量/访存等执行资源
软件：kernel grid → 可选cluster → CTA/block → warp → thread/lane
矩阵：输出tile → MMA逻辑tile → 各线程的fragment

三条层级相互映射，但不是一一对应。cluster通过显式API让CTA协作，硬件调度保证所需的共驻留；它不是任意挑选两个物理SM或两个die。

04 / 从内存到矩阵单元

同样是 GEMM，两代芯片的 accumulator 去向不同

下面选择的是现代高性能路径，而非所有 kernel 都必须遵循的唯一流程。H20 可以用其他 MMA 路径；B200 也可以运行兼容代码，但要评估是否真正利用了新架构。

TMA 与 TMEM 不是同一概念。TMA 是搬运机制；SMEM 是共享存储；TMEM 是 Blackwell 的 Tensor Core 专用存储。Hopper WGMMA 的 accumulator 在寄存器，Blackwell tcgen05 的结果首先写到 TMEM，再按需要搬到寄存器做缩放或 epilogue。
HOPPER / H20 · 从工作分工到硬件执行

H20：一个 SM 内，搬运与矩阵计算怎样合作？

把 SM 理解成可驻留多个 CTA 的计算单元，把 tile 理解成程序选择的一块矩阵。SM 数由芯片决定；tile 数由 M/N/K 和 BM/BN/BK 决定。一个 SM 能先后处理很多 tile，同一时刻的驻留数还要看寄存器和 shared memory。

Warp、warpgroup、CTA：三个不同层级

对象规模在 GEMM 中干什么
Warp32 threads / lanes基本指令执行分组。NVIDIA warp32 与 MI355X wave64 不能按线程数直接互换调优配置。
Warpgroup4 个连续、按 4 对齐的 warps = 128 threadsHopper wgmma.mma_async 的协作范围；共同发起一次 WGMMA，结果 fragment 分布在参与线程的寄存器中。
CTA / thread block程序决定线程数，可含多个 warps/warpgroups同一 CTA 在同一个 SM 上执行，拥有自己的 shared memory 和组内同步。一个 producer warpgroup + 两个 consumer warpgroups 是可选设计，不是硬件固定配置。
Thread block cluster多个 CTA 的显式协作组可跨 SM、在同一 GPC 内协同驻留，使用 distributed shared memory 或 TMA multicast；普通 CTA 不会自动获得这些能力。

一个 CTA 不必只负责一个 tile：persistent kernel 可以让同一批 CTA 从任务调度器不断领取新 tile；反过来，Global Split-K 也可以让多个 CTA 计算同一个输出 tile 的不同 K 段。

128 粒度 FP8 blockscale：缩放发生在哪里？

沿用 A8W8 场景：A 的 scale 可按每行、每 K128 一份，W 的 scale 可按每 N128×K128 一份。具体 shape 和布局仍以算子接口为准。

C[m,n] = Σg { dot(A_fp8[m,128g:128g+128],
                     W_fp8[n,128g:128g+128])
                 × sA[m,g] × sW[floor(n/128),g] }

Hopper 普通 FP8 WGMMA 不会自动消费这些任意 FP32 scale 张量。内核要让不同 K128 的部分和分别缩放后再合并。WGMMA 的立即数缩放/累加开关也不是这个 blockscale 接口。若 scale 随 K 分组变化，不能把所有 K 的裸 dot 相加后只在最终 epilogue 乘一次 scale。

FP8 WGMMA 的一条指令可采用 m64nNk32 家族；算法的一个 K128 分组会包含若干次指令 K32 步进。指令 K、软件 BK、量化 group K128 是三种粒度，sweep 要保持三者的分组与归约语义正确。

BLACKWELL · SM100

B200：两个 die 组成一个 GPU，新增 TMEM 计算通路

对 kernel 开发最有用的变化，是 Tensor Core 的输入、累加与线程寄存器进一步分离：TMA 搬数据，SMEM 缓冲输入，tcgen05.mma 做矩阵计算，TMEM 保存累加结果。

一次 GEMM tile 的数据旅程

01 · INPUT

HBM → L2 → SMEM

A/B 的 FP8 tile 与 scale 从显存读取。producer 对 A/B 发起 TMA，异步写入 SMEM 的下一阶段缓冲；FP32 scales 可以采用独立加载路径；mbarrier 表示数据已经就绪。

02 · MMA

SMEM → Tensor Core → TMEM

等待输入后发起 tcgen05.mma。典型路径 A/B 在 SMEM，FP32 累加在 TMEM；PTX 也允许 A 来自 TMEM。计算与后续 tile 搬运重叠。

03 · EPILOGUE

TMEM → 寄存器 → 输出

tcgen05.ld 将结果读到线程寄存器。当前K128软件blockscale在每个分组读回后缩放累加；完成全部K后，再执行bias、激活或类型转换；通过 global store 或 SMEM + TMA store 写出。

异步流水的核心：buffer 0 正在计算时，buffer 1 可以装入下一块。必须在“读输入前”及“覆盖旧 buffer 前”分别满足同步条件；多设 stages 本身不保证更快。

为什么 tcgen05 与 Hopper 的 WGMMA 不一样？

操作SM100 的执行要求正确理解
tcgen05.mma单线程可发起，计算异步完成发起者少，不代表整块 GEMM 只需要一个线程；加载、同步、结果搬运仍需要协作
TMEM alloc/dealloc1CTA 路径需一个 warp；2CTA 路径需两边各一个 warp 集体参与“single-thread issue”不能推广到全部 TMEM 指令
TMEM load/store一个 warp 可访问本 CTA TMEM 的 1/4；完整范围需要一个 warpgroup结果读取仍有固定 lane/layout 规则
1SM / 2SM MMA一 CTA 或同一 cluster 中的一对 CTA 合作2SM 可让更大的 MMA tile 协作执行，并增加布局、同步和调度约束

普通 CTA 的所有线程仍在一个 SM 内执行。2SM 路径是两个 CTA 各自在一个 SM 上，通过专门指令协作；不是一个 CTA 被拆到两个 SM，也不是 global Split-K。

保留你的 FP8 × FP8、128 粒度 scale 语义

你目前的 K128 blockscale 与 Blackwell 的 MXFP8 硬件 microscaling 并不自动相同。MXFP8 常见 K32 分组、E8M0 scale，还要求特定 scale 布局。保留原语义时，每个 K128 分组的 dot 必须先结合它自己的 scale，再合并到最终结果；跨不同 scale 分组的裸 dot 不能先合并后统一乘一次 scale。

评估 MXFP8 路径时，将重新量化/scale 转换视为数值合同变化：验证误差，并分别报告转换开销、纯 GEMM 延迟与完整算子延迟。TMEM、SMEM 和 scales 的具体布局由选用的 kernel 决定。

依据：Blackwell Tuning Guide · PTX Tensor Memory · tcgen05 发起粒度 · CUTLASS Blackwell · DGX B200 规格 · 官方技术简报。核对日期：2026-10-19。

06 / 沿用你的 FP8 A8W8 目标

128 粒度 FP32 blockscale，要与原生 MXFP8 分开比较

D[m,n] ≈ Σg sA[m,g] × sW[⌊n/128⌋,g] × Σ(k∈group g) AQ[m,k] × WQ[n,k]
sA：逻辑 [M, ceil(K/128)]；sW：逻辑 [ceil(N/128), ceil(K/128)]；group g 长度 128。

数学合同可以保持一致，但不能把 AITER 的 shuffle_weight 输出或特殊 A-scale 字节布局，直接交给 NVIDIA kernel。需要按目标 API 的 stride、量化值布局、scale 布局、TMA descriptor 和对齐要求重新准备数据。

路线scale 语义与执行方式与当前问题是否相同
Hopper FP8 blockwiseWGMMA 算各 K 分组的 FP8 dot，使用软件处理 FP32 scales，再累加。可以实现当前合同；kernel 必须支持对应 A/B scale 几何。
Blackwell FP8 blockwise / groupwisetcgen05 产生 TMEM 部分和；按实现读到寄存器做 FP32 分组缩放与总和累加。可以实现当前合同；这条路线不能仅写“用了原生硬件缩放”。
Blackwell MXFP8 block-scaled MMA典型每 32 个元素一个 E8M0（幂次）scale，使用对应 scale layout 与原生矩阵指令。不是任意 FP32 scale128 的等价替换；量化误差和准备流程都可能改变。
Blackwell NVFP4典型 16 元素 scale block、E4M3 scale 配合额外全局尺度；数据是 FP4。已经改变输入精度与量化合同，不能把加速全部算作同一个 FP8 kernel 的优化。
库中新增加的 scale 模式还可能有 UE8M0 的 128 等模式；版本、架构、shape 和 scale 编码有限定。要逐 API 检查，不能仅凭“128”或“blockscale”同名判等。
先固定数值，再比速度：用同一份 FP8 数值和逻辑 FP32 scales 建参考，分开测量权重准备、激活动态量化、主 GEMM、必要缩放/归约和最终 epilogue。静态 W 的预排布可摊销；每次生成的 A 与 scales 不能凭空省略。

BK=256 若跨两个 K128 分组，就要分别应用两组 scales；不能先把两组的裸 dot 混合后只乘一个 scale。BK 是否可取 128/256 还要看具体指令、copy pipeline 与实例约束。

推荐的四轮实验

  1. 同合同基线：保存当前实现与库候选；固定 M/N/K、dtype/scales、stride、workspace 和运行模式。
  2. 粗搜结构：按 shape 分组，选实现已有的合法 tile/pipeline。小 M 先验证工作是否足够，大 GEMM 先看算力与搬运是否重叠。
  3. 局部搜索：保留 top-k，扫 stages、cluster、raster/swizzle、warp 分工；这些轴互相影响，不能永远只调一个轴。
  4. 独立复测：验证数值、缓存条件与正式计时，最后在真实调用路径中验证配置命中和端到端收益。
选择赢家的目标：相同数值合同下的完整算子耗时与业务加权总时间。不是更高 occupancy、更大的 tile 或更多 Tensor Core 数量本身。
08 / 固定版本的可运行起点

GEMM 如何 sweep：先锁定数学契约，再搜索执行方案

沿用你关心的 FP8 A8W8、128 粒度 blockscale。下列示例采用常见的 A 每行 K128 一份 FP32 scale，W 每个 N128×K128 块一份 FP32 scale，输出 BF16。如果实际 scale 形状不同，应先修改契约再比较。AMD 的 B preshuffle 布局不能直接作为 NVIDIA kernel 的输入布局。

峰值只对同 dtype、dense/sparse、GPU SKU、功耗/时钟、正确算术量比较。宣传表上的 structured sparsity 峰值不能拿来算 dense GEMM 利用率。
集成记录实际 dispatch、量化/scale转换、pack、workspace、reduction 与融合操作。GEMM-only 变快不保证整个 FP8 调用路径变快。

查询真实 SM 数和可见设备参数

在目标服务器上先用 nvidia-smi 查询型号、驱动、显存与功耗上限；如果环境已经安装 CUDA 版 PyTorch，再运行下方内联命令读取当前进程可见的设备与 SM 数。

nvidia-smi --query-gpu=name,driver_version,memory.total,power.limit --format=csv

python3 - <<'PY'
import torch

print("PyTorch:", torch.__version__)
print("PyTorch CUDA build:", torch.version.cuda)
print("CUDA available:", torch.cuda.is_available())
for i in range(torch.cuda.device_count()):
    p = torch.cuda.get_device_properties(i)
    print(f"Device {i}: {p.name}")
    print(f"  Compute capability: {p.major}.{p.minor}")
    print(f"  Visible SMs: {p.multi_processor_count}")
    print(f"  Visible memory: {p.total_memory / 2**30:.2f} GiB")
    print("  Device properties:", p)
PY

这些查询不运行 GEMM。PyTorch 的 CUDA build 版本不是驱动版本；nvidia-smi 顶部 CUDA Version 表示驱动支持的 CUDA 版本上限。显存 GiB 与产品表 GB 需统一单位；MIG 或其他分区、CUDA_VISIBLE_DEVICES 会影响当前进程可见设备。L2、shared、寄存器和 cluster 上限应进一步用对应 CUDA 版本的设备属性 API 或 Nsight Compute 核验，不能仅由 SM 数推断。
